# HospAI current state: platform-side (multi-tenant SaaS) capabilities and plans

Read-only review of the hospai-core repo on 2026-11-22 (branch `main`, HEAD `29a3fdf`). Links are relative to this file and point into the repo (`../../../../` is the repo root). "Shipped" means code exists in the tree; "planned" means it is only in ARCHITECTURE.md, the roadmap or a spec. Items marked *(inferred)* are my reading, not a stated fact. No secret values are copied here.

## 1. How are orgs and properties modelled, and is there anything above an org or between org and property?

### Takeaway
There are two tenant levels: Organization (the billing customer) and Property (the hotel). Each has its own Durable Object (OrgDO, PropertyDO), plus an OrgEntitlementDO for each org. One global Platform D1 database holds the tenant registry and the entitlement catalog. Nothing in the code sits between org and property (no brand or group entity), and there is no platform-operator tier in the data model. The architecture names "property-group" role scopes and a GroupAvailabilityDO, but neither exists in code.

### Cited Findings
- The tenancy model is `Organization (billing entity, the customer) → Property → Unit/Room`. Users belong to an Organization and "hold roles scoped to (org | property | property-group)". — [ARCHITECTURE.md §2](../../../../ARCHITECTURE.md)
- Isolation is structural, not row-level: one PropertyDO (SQLite) per property, one OrgDO per org, and one shared global "Platform control plane" D1. Both tenant tiers are addressed with `getByName(id)`, and the tenant-router is called "the most security-critical code in the system". — [ARCHITECTURE.md §2](../../../../ARCHITECTURE.md)
- The topology has three DO classes (PropertyDO, OrgDO, OrgEntitlementDO) and Platform D1. OrgEntitlementDO is kept apart from OrgDO "on purpose", so that hard-limit counters are never read stale. — [ARCHITECTURE.md §3](../../../../ARCHITECTURE.md); bindings `PROPERTY_DO`, `ORG_DO`, `ORG_ENTITLEMENT_DO` in [apps/pms-core/wrangler.jsonc](../../../../apps/pms-core/wrangler.jsonc)
- OrgDO holds users, role assignments, guest profiles (PII vault), rate plan definitions, the property registry, org settings and the audit log. Cross-org scans are meant to go to an "Iceberg warehouse, never to OrgDO". — [ARCHITECTURE.md §4.3](../../../../ARCHITECTURE.md)
- The Platform D1 registry is in code. Table `org` has (`org_id`, `name`, `status`, `created_at`, plus `closing_at` and `purge_not_before` added later). Table `property` has (`property_id`, `org_id`, `name`, `jurisdiction` ∈ {eu, us, fedramp} or NULL, `time_zone`, `status`). A trigger makes jurisdiction immutable. — [migrations/d1-platform/0001_tenant_registry.sql](../../../../migrations/d1-platform/0001_tenant_registry.sql), [0004_purge.sql](../../../../migrations/d1-platform/0004_purge.sql)
- Org and property rows can never be deleted (triggers `org_no_delete`, `property_no_delete`). Org status moves active → closing → purging → purged, and closing can go back to active. Property status moves active → purging → purged. — [migrations/d1-platform/0004_purge.sql](../../../../migrations/d1-platform/0004_purge.sql)
- The registry is the fan-out source of truth because "DOs cannot be enumerated"; registry writes are "never best-effort". — [ARCHITECTURE.md §12](../../../../ARCHITECTURE.md)
- Roles in code are `OrgRole = 'owner' | 'admin' | 'staff'`, held at org level and per property (OrgDO table `property_member (user_id, property_id, role)`). Permissions are split into `ORG_SCOPED_PERMISSIONS` (`org:read`, `org:manage`, `org:cancel`, `org:purge`, `property:provision`) and about 34 property-scoped ones. No property-group scope exists in contracts, pms-core or migrations (grep for `property_group`/`propertyGroup` found nothing). — [packages/contracts/src/permissions.ts](../../../../packages/contracts/src/permissions.ts), [migrations/do-org/0004_property_member.sql](../../../../migrations/do-org/0004_property_member.sql)
- The only "platform" permission is `PLATFORM_ONLY_PERMISSIONS = ['shell:internal']`. It gates two SPA-shell catalog commands (`shell.set_role`, `shell.set_property`), not an operator console. — [packages/contracts/src/permissions.ts](../../../../packages/contracts/src/permissions.ts), [packages/contracts/src/commands/catalog.ts](../../../../packages/contracts/src/commands/catalog.ts)
- System actors are `night_audit`, `night_audit.auto_transfer`, `migration_sweep`, `queue_replay`, `provision`, `purge`, `auth_hold_lapse` and `event_consumer`. There is no support or operator human actor kind. — [packages/contracts/src/permissions.ts](../../../../packages/contracts/src/permissions.ts)
- The multi-property design is planned, not built. A GroupAvailabilityDO projection "per property-group", two-phase central reservations, chain reporting from the warehouse, and cross-property rate push as a BULK-lane Workflow are listed. Guest profiles are already org-wide in OrgDO. — [ARCHITECTURE.md §7.6](../../../../ARCHITECTURE.md)
- The operator SPA is bound to one org and one property at build time, through `VITE_ORG_ID` / `VITE_PROPERTY_ID` (`readTenantConfig` throws `tenant_config_missing` without them). The staging deploy sets them from repo variables. — [apps/web-pms/src/config/tenant.ts](../../../../apps/web-pms/src/config/tenant.ts), [.github/workflows/staging-deploy.yml](../../../../.github/workflows/staging-deploy.yml)
- Org-level HTTP routes in code: `post_orgs` (bootstrap), `post_org_properties`, `get_org_properties`, `get_org_entitlements`, `list/create/update/delete_org_member`, `post_org_cancel`, `post_org_purge`, `get/put_org_guest_settings`. — [apps/pms-core/src/v1-dispatch.ts](../../../../apps/pms-core/src/v1-dispatch.ts) (`V1_ROUTES`)

### Inferences
- *(inferred)* Because the SPA build carries one property id, a multi-property org today needs a separate SPA build per property, or the yet-to-ship R4.4 switcher. The server already supports several properties per org (`get_org_properties`, property-scoped roles).
- *(inferred)* No operator, reseller or management-company tier exists. A hotel management company running hotels for different owners would have to be one org (shared billing) or several unlinked orgs.

### Gaps
- No design for brand or management-company hierarchies (owner vs operator vs brand) was found in ARCHITECTURE.md or the specs.
- I did not read OrgDO's internal property-registry schema in full (`migrations/do-org/0001_org_spine.sql`), only the registry calls.

## 2. How is a new tenant created today, and who can do it?

### Takeaway
Self-service through the API. Any authenticated Clerk user can call `POST /v1/orgs`, becomes `owner`, and gets a Starter subscription seeded automatically. An owner or admin then calls `POST /v1/orgs/:orgId/properties` (permission `property:provision`, entitlement `pms.core`). That call is capped by the hard `pms.properties.limit` counter. There is no sign-up UI, onboarding wizard, operator provisioning tool or plan-assignment tool. Demo seeding is local-only.

### Cited Findings
- `post_orgs` has `scope: 'bootstrap'`. The dispatcher skips tenant and permission resolution for bootstrap routes. The handler validates `orgId`/`name`, calls `createOrg`, returns 409 `org_exists` on collision, then `ensureMember(actor.userId, 'owner')`. — [apps/pms-core/src/v1-dispatch.ts](../../../../apps/pms-core/src/v1-dispatch.ts) (`handlePostOrgs`, `dispatchV1`)
- Keeping authenticated `POST /v1/orgs` bootstrap is a recorded decision: "isolation is the org-match on provision, plus `azp`". — [AGENTS.md "Do not fix these"](../../../../AGENTS.md)
- Creating an org row also seeds a `starter` subscription (`upsertOrg` → `seedSubscription(env, orgId, 'starter')`). — [apps/pms-core/src/registry.ts](../../../../apps/pms-core/src/registry.ts)
- `provisionProperty` does these steps in order: validate ids, gate on an existing org being active, validate timezone (which gives the locationHint) and currency, reject a global `propertyId` owned by another org (`property_exists`) or with a different jurisdiction, `reservePropertySlot` in OrgEntitlementDO (`limit_exceeded` / `pms.properties.limit` at cap), insert the registry row (releasing the slot if that fails), then sync OrgDO membership and property ref and initialise PropertyDO (jurisdiction, ids, timezone, currency, business date, night-audit alarm). — [apps/pms-core/src/provision.ts](../../../../apps/pms-core/src/provision.ts)
- The route is `post_org_properties`, `POST /v1/orgs/:id/properties`, `permission: 'property:provision'`, `entitlement: 'pms.core'`. — [apps/pms-core/src/v1-dispatch.ts](../../../../apps/pms-core/src/v1-dispatch.ts)
- The cross-tenant provision graft (audit S1/S3/G1) was fixed in R0.1: org match, 409 with no foreign row. — [docs/roadmap.md Track 0](../../../../docs/roadmap.md); spec [2026-09-04-cross-tenant-provision-design.md](../../../../docs/superpowers/specs/2026-09-04-cross-tenant-provision-design.md)
- The pilot tenant is to be "provisioned by ops on Growth with `pos.enabled` and `ai_ops.enabled`", listed as a go-live step, not a coding slice. — [docs/roadmap.md Track P "Provisioning" and "Pilot go-live"](../../../../docs/roadmap.md)
- Plan changes have no HTTP route. `seedSubscription` (in registry.ts, used by provisioning and tests) is the only code path that updates `plan_code` (`UPDATE subscription SET plan_code = ?, … entitlement_version + 1`). Plan or add-on purchase UI and SPA plan changes are deferred to R5.6. — [apps/pms-core/src/registry.ts](../../../../apps/pms-core/src/registry.ts); [docs/superpowers/specs/2026-11-18-entitlement-catalog-design.md §2](../../../../docs/superpowers/specs/2026-11-18-entitlement-catalog-design.md)
- `post_demo_seed` and `post_migration_sweep` are `scope: 'dev'`. They only work when `HOSPAI_UNSAFE_LOCAL === '1' && HOSPAI_ALLOW_DEV_ACTOR === '1'`, otherwise they return 404. `scripts/demo-reset.mjs` "wipe[s] local wrangler state, start[s] pms-core, seed[s] demo hotel" with `--profile india|us`. — [apps/pms-core/src/env.ts](../../../../apps/pms-core/src/env.ts) (`isDevActorAllowed`), [scripts/demo-reset.mjs](../../../../scripts/demo-reset.mjs)
- The prototype `OnboardingDashboard.tsx` (first-hotel wizard) maps to "demo seed only | R4.2 ops". — [docs/roadmap.md prototype → live map](../../../../docs/roadmap.md)
- The staging smoke creates a fresh `org_smoke_<timestamp>` and property on every run, then runs room types, rates, guest, room, book, assign, check-in, COMPANY window transfer and city-ledger AR, invoice, check-out. — [scripts/smoke-staging.mjs](../../../../scripts/smoke-staging.mjs)

### Inferences
- *(inferred)* "Ops provisioning on Growth with add-ons" can only be done today with direct SQL against Platform D1 (`subscription`, `subscription_addon`), for example through `wrangler d1 execute`. No runbook for this was found.
- *(inferred)* Every staging smoke run leaves a new org and property behind. No cleanup step was found in the script.

### Gaps
- No documented production provisioning runbook (who creates the org, how the plan is set, how the first owner's Clerk account is linked).

## 3. What does the entitlement system cover, where is it stored and changed, is there an operator UI, and what is the kill-switch?

### Takeaway
The entitlement plane is built end to end. Platform D1 holds the catalog: 22 feature keys, plans Starter/Growth/Group, add-ons and per-org add-on quantities. OrgEntitlementDO resolves a snapshot. KV caches it under a version key, and the DO keeps a 60-second cache. Only `pms.core` and the hard `pms.properties.limit` are enforced today; the other keys exist for later slices. There is no operator UI to change plans, add-ons or overrides, and no `entitlement_override` table. The kill-switch is a global KV key per feature (`kill:<featureKey>`), not per tenant. It returns 503 and can only be set by a test helper or a raw KV write.

### Cited Findings
- Three gating planes (Entitlements in Platform D1, Permissions in OrgDO, Feature flags in KV) plus a separate operational kill-switch and a configuration plane. "A gated feature must pass all three independently." — [ARCHITECTURE.md §1](../../../../ARCHITECTURE.md)
- The planned D1 model includes `entitlement_override (org_id, feature_key, value, reason, granted_by, expires_at)` and `usage_counter`. The resolution order is plan → add-ons → trial grants → tenant overrides → delinquency policy ("past-due → read-only, not blackout"). — [ARCHITECTURE.md §6.1–6.2](../../../../ARCHITECTURE.md)
- Shipped D1 tables: `feature`, `plan`, `plan_feature`, `subscription` (`plan_code`, `status`, `entitlement_version`, `trial_ends_at`, `current_period_end`) and, from migration 0006, `addon` and `subscription_addon`, whose triggers bump `entitlement_version`. `entitlement_override` and `usage_counter` do not appear in any migration or source file. — [migrations/d1-platform/0002_entitlements.sql](../../../../migrations/d1-platform/0002_entitlements.sql), [0006_entitlement_catalog.sql](../../../../migrations/d1-platform/0006_entitlement_catalog.sql)
- Subscription invariants: rows are never deleted, status is `active` or `cancelled`, and `entitlement_version` is monotonic and must rise on any plan or status change. — [migrations/d1-platform/0003_subscription_invariants.sql](../../../../migrations/d1-platform/0003_subscription_invariants.sql)
- R3.10 (done 2026-11-18): `FEATURE_KEYS` holds the 22 §6.7 keys. Starter, Growth and Group are seeded cell for cell; there is no Enterprise tier. Add-ons are read by the resolver, but "nothing sells add-ons until R5.6". `pms.properties.limit` is enforced as a hard limit in OrgEntitlementDO (`422 limit_exceeded`). Enforcing `payments.enabled` enrolment is R4.7. — [docs/roadmap.md R3.10](../../../../docs/roadmap.md)
- Out of scope for the catalog slice: "Billing, prices, Stripe, plan or add-on purchase UI, plan changes from the SPA (all R5.6) … enforcing units, channel connections, MCP clients, AI messages (their slices); any gate on a feature key other than `pms.core`". — [docs/superpowers/specs/2026-11-18-entitlement-catalog-design.md §2](../../../../docs/superpowers/specs/2026-11-18-entitlement-catalog-design.md)
- Package design: three tiers (Starter / Growth / Group), "deliberately no Enterprise tier", groups of 3–10 properties. `pms.properties.limit` is 1/1/10 with a +1 add-on. `pms.multi_property` is Group-only. `pos.enabled`, `ai_ops.enabled`, `revenue_mgmt.enabled`, `banquet.enabled` are add-ons. `accounting_export.enabled` and `compliance.fiscalization` are on every tier. — [ARCHITECTURE.md §6.7](../../../../ARCHITECTURE.md)
- Distribution: `loadSnapshot` reads the active `entitlement_version` from D1, then KV key `ent:<orgId>:v<version>` (expiration TTL 3600 s), falling back to `OrgEntitlementDO.resolveEntitlements`. `EntitlementDoCache.MAX_AGE_MS = 60_000`. — [packages/entitlement-client/src/index.ts](../../../../packages/entitlement-client/src/index.ts)
- OrgEntitlementDO has `resolveEntitlements`, `checkHardLimit`, `reservePropertySlot`, `releasePropertySlot`, and DO-local tables `meter_counter` and `standing_counter`. — [apps/pms-core/src/org-entitlement-do.ts](../../../../apps/pms-core/src/org-entitlement-do.ts), [packages/do-runtime/src/entitlement-migrations.ts](../../../../packages/do-runtime/src/entitlement-migrations.ts)
- The tenant-facing read is `get_org_entitlements` (`GET /v1/orgs/:id/entitlements`, `org:read`). The SPA uses it through `use-entitlements.ts` to gate UI. — [apps/pms-core/src/v1-dispatch.ts](../../../../apps/pms-core/src/v1-dispatch.ts), [apps/web-pms/src/shell/use-entitlements.ts](../../../../apps/web-pms/src/shell/use-entitlements.ts)
- Error mapping: `entitlement_required` → 402. Kill-switch or resolution failure → 503 ("An infrastructure incident must not surface as 402"). — [docs/superpowers/specs/2026-07-28-entitlements-killswitch-design.md](../../../../docs/superpowers/specs/2026-07-28-entitlements-killswitch-design.md); [AGENTS.md §3 table](../../../../AGENTS.md)
- Kill-switch in code: `checkKillSwitch` reads `ENTITLEMENT_KV` key `kill:${featureKey}` with `cacheTtl: 60`. `dispatchV1` checks it for any route that declares an entitlement, and additionally checks `kill:pms.core` for `post_org_cancel` and `post_org_purge`. A hit returns `503` with an empty body. — [packages/entitlement-client/src/index.ts](../../../../packages/entitlement-client/src/index.ts); [apps/pms-core/src/v1-dispatch.ts](../../../../apps/pms-core/src/v1-dispatch.ts) (`dispatchV1`)
- The cache TTL differs between docs and code: the architecture and the kill-switch spec say `cacheTtl: 10`, the code uses `cacheTtl: 60`. — [ARCHITECTURE.md §6.4](../../../../ARCHITECTURE.md) vs [packages/entitlement-client/src/index.ts](../../../../packages/entitlement-client/src/index.ts)
- Kill-switch tooling: `setKillSwitch` is commented "Test-only". The spec says "Operational tooling (Vitest helper …) for tests only in Phase 0". Applying the kill-switch to alarms and queue consumers is a deferred hazard. — [apps/pms-core/src/registry.ts](../../../../apps/pms-core/src/registry.ts); [docs/superpowers/specs/2026-07-28-entitlements-killswitch-design.md](../../../../docs/superpowers/specs/2026-07-28-entitlements-killswitch-design.md)
- Kill-switch policy: "may leave membership mutations up. Must block org cancel and purge … New un-entitled mutating routes must say explicitly whether the kill-switch applies." — [AGENTS.md §1](../../../../AGENTS.md)
- Release feature flags (the §1 KV plane) have no implementation: grep for a flag KV or `releaseFlag` found nothing. — repo grep over `apps/pms-core/src`, `packages/*/src`

### Inferences
- *(inferred)* The kill-switch is keyed by feature only, so it is fleet-wide (for example `kill:pms.core` stops every tenant's entitled routes). There is no per-tenant suspend switch apart from org `status` (`assertTenantActive`) and subscription `status`.
- *(inferred)* Changing a tenant's plan, granting an add-on or setting a sales concession needs hand-written D1 SQL today. The triggers keep the version bumps correct, but nothing records who granted it or why, because `entitlement_override` with `reason`/`granted_by` does not exist.

### Gaps
- No trial-expiry, delinquency or dunning logic was found. `trial_ends_at` and `current_period_end` exist as columns, but I found no code that reads them for resolution (not exhaustively verified).

## 4. Is there a platform or operator console, billing integration, usage metering or customer health tracking?

### Takeaway
None of these exist in code. The architecture specifies a separate admin-console Worker behind Cloudflare Access with time-boxed, dual-controlled support elevation, but nothing is built. Billing (Stripe, self-serve plans, usage billing) is roadmap R5.6 in the Canada-launch track. Metering exists only as DO counter tables. No Analytics Engine binding and no customer-health signal exist.

### Cited Findings
- Planned support access: "Nobody holds tenant access at rest." The `ElevationGrant` has READ (self-service with reason and ticket, ≤60 min) and WRITE (dual control, ≤15 min, one property, one named operation, through domain commands only). Support access shows in the tenant's own audit log. A break-glass raw-SQL credential opens an incident. Global revocation happens through the kill-switch. There is a weekly elevation review. "The admin console is a separate Worker behind Cloudflare Access with hardware-key enforcement." — [ARCHITECTURE.md §4.9](../../../../ARCHITECTURE.md)
- No `ElevationGrant`, elevation or admin-console code exists in `apps/`, `packages/` or `modules/` (grep found nothing). The only `/v1/admin/*` route is the dev-only `post_migration_sweep`. — repo grep; [apps/pms-core/src/v1-dispatch.ts](../../../../apps/pms-core/src/v1-dispatch.ts)
- Deployed Workers: one Worker (`hospai-pms-core`, plus `-staging`), which also serves the SPA through `assets`. The planned `edge`, `payments` and `booking-engine` Workers do not exist yet. — [apps/pms-core/wrangler.jsonc](../../../../apps/pms-core/wrangler.jsonc); [ARCHITECTURE.md §3 Phased Worker deployment](../../../../ARCHITECTURE.md)
- R5.6 "Self-serve plans + usage billing" (unticked, Track 4): "Stripe billing for plan changes; metered add-on usage". It moved into the Canada launch because Starter needs payments enrolment at provisioning. — [docs/roadmap.md Track 4](../../../../docs/roadmap.md)
- Phase 3 in the architecture lists "Self-serve plan changes + Stripe billing" and "Usage billing for metered add-ons". — [ARCHITECTURE.md §14 Phase 3](../../../../ARCHITECTURE.md)
- Planned metering: `hard` (OrgEntitlementDO counter), `soft` (Analytics Engine → billing rollup), `grace` (allow overage and notify). The KV/R2 table names "Analytics Engine — soft meters, per-tenant usage telemetry". — [ARCHITECTURE.md §4.7, §6.6](../../../../ARCHITECTURE.md)
- No Analytics Engine binding or `writeDataPoint` call exists in pms-core or packages. The wrangler config has no `analytics_engine_datasets`. — repo grep; [apps/pms-core/wrangler.jsonc](../../../../apps/pms-core/wrangler.jsonc)
- `plan.base_price` exists (seeded 0) with `billing_interval` 'month'. — [migrations/d1-platform/0002_entitlements.sql](../../../../migrations/d1-platform/0002_entitlements.sql)
- In-tenant admin surfaces that do exist: Settings (users, system, logs, tax, documents and more), Staff/Roster, Exceptions, Event delivery section, and org member CRUD routes. All are for the hotel's own staff, not the platform operator. — [apps/web-pms/src/screens](../../../../apps/web-pms/src/screens) (e.g. `settings-users.tsx`, `settings-logs.tsx`, `EventDeliverySection.tsx`, `ExceptionsScreen.tsx`)

### Inferences
- *(inferred)* Platform-side tenant management (list tenants, see plan and status, suspend, change plan, impersonate or support) would today be done with Cloudflare dashboard and `wrangler` against D1/KV. That is the gap §4.9 was written to close.
- *(inferred)* The pilot runs on Growth, which grants `payments.enabled`, so the pilot needs no billing system. Invoicing the hotel for HospAI would happen outside the product.

### Gaps
- No customer health, NPS, adoption or usage dashboard is planned anywhere I searched (ARCHITECTURE.md, roadmap). The warehouse (§4.9 path 1) is the named home for "ops dashboards" but has no slice.

## 5. What exists for logging, metrics, alerts, status pages and on-call, and what is planned?

### Takeaway
What exists: tenant-tagged structured JSON logs (`@hospai/observability`), outbox flush and backlog log lines, a per-property event-consumer exception queue, and a degraded-mode exception workbench in the SPA. There is no wrangler `observability` block, no OpenTelemetry or exporter, no metrics, no alerting or paging, no status page, no SLOs and no on-call setup. The architecture lists ten per-property paging signals as the target, and the observability spec defers alerting to "Phase 1 ops". No roadmap slice owns it.

### Cited Findings
- Phase 0 observability "does not ship a full OpenTelemetry → Baselime/Axiom pipeline; it ships the tagging contract, structured log helpers, and the backlog signals". Scope out: "OpenTelemetry SDK, trace propagation …", "Metrics export (StatsD, Analytics Engine)", "Per-fleet dashboards, paging, SLO definitions (§13 table is the target; alerting is Phase 1 ops)". DLQ depth is "via wrangler/dashboard". — [docs/superpowers/specs/2026-07-28-observability-design.md](../../../../docs/superpowers/specs/2026-07-28-observability-design.md)
- `@hospai/observability` exports `logInfo`, `logWarn`, `logError`, `logFields` and `parseLogLine`. The Worker entry logs each `/v1` request and asset failures. Outbox logs `outbox.flush`, `outbox.deferred` and `outbox.flush_failed`. — [packages/observability/src/index.ts](../../../../packages/observability/src/index.ts), [apps/pms-core/src/index.ts](../../../../apps/pms-core/src/index.ts), [apps/pms-core/src/outbox-observability.ts](../../../../apps/pms-core/src/outbox-observability.ts)
- Tagging contract: `org_id`, `property_id`, `module_id` and user id on every log. Unknown tags are omitted. — [docs/superpowers/specs/2026-07-28-observability-design.md](../../../../docs/superpowers/specs/2026-07-28-observability-design.md); [ARCHITECTURE.md §13 Observability](../../../../ARCHITECTURE.md)

## 6. What do ARCHITECTURE.md, the roadmap, AGENTS.md and the specs say about multi-property, platform operations, warehouse/analytics (§7.8), purge, release management, backups, migration/import, public API, compliance and the production environment?

### Takeaway
Compliance is the most mature platform area: crypto-shredding with per-org HKDF keys, a seven-step purge Workflow with certificates, an org close → 30-day retention → purge lifecycle, financial and immigration exemptions, and documented residency rules. Release management is basic: CI gates, a manual staging deploy that checks for a green CI run, and an HTTP smoke. Production resources exist, but there is no production deploy workflow, no production Clerk instance and no feature flags. Backups and restore, the warehouse, data import, the public API and multi-property views are all designed or roadmapped, not built.

### Cited Findings
**Release management**
- CI (`ci.yml`, on push) jobs: `checks`, `test-pms-core` (8 shards), `test-pms-core-ledger-prop`, `test-pms-core-migration-sweep`. 17 `check:*` gates are merge-blocking. — [.github/workflows/ci.yml](../../../../.github/workflows/ci.yml); [AGENTS.md "Merge-blocking gates"](../../../../AGENTS.md)
- `staging-deploy.yml` runs on `workflow_dispatch` (manual). Job `verify-ci-green` checks that a CI run succeeded (it can be skipped with `skip_ci_check`). Then it sets secrets with `wrangler secret put`, runs `wrangler d1 migrations apply hospai-platform-staging --remote`, runs `wrangler deploy --env staging`, mints a Clerk session for a smoke user and runs `pnpm smoke:staging`. — [.github/workflows/staging-deploy.yml](../../../../.github/workflows/staging-deploy.yml)
- Rule: "Staging deploy must not outrun a green CI SHA." Extend `scripts/smoke-staging.mjs`; do not add Playwright as the first e2e layer. — [AGENTS.md §5](../../../../AGENTS.md)
- Staging rollback is a teardown procedure (`wrangler delete`, delete D1, KV, R2 and queues), not a version rollback. — [docs/superpowers/specs/2026-08-16-staging-deploy-smoke-design.md Lock 7](../../../../docs/superpowers/specs/2026-08-16-staging-deploy-smoke-design.md)
- Production environment, started 2026-11-19: `env.production` points at real resources (R2 `hospai-event-log` and `hospai-guest-docs` with Asia-Pacific hints, three queues and three DLQs, three KV namespaces, D1 `hospai-platform` in Asia-Pacific with all six platform migrations applied). Still to do: a Clerk production instance ("until then auth fails closed"), the `CLERK_SECRET_KEY` and `HOSPAI_ORG_MASTER_KEY` secrets ("a new master key, never the staging one"), and "a production deploy workflow gated on green CI like `staging-deploy.yml`". — [docs/roadmap.md Pilot go-live](../../../../docs/roadmap.md); [apps/pms-core/wrangler.jsonc](../../../../apps/pms-core/wrangler.jsonc) (production `vars` holds only `CLERK_AUTHORIZED_PARTIES`)
- Unsafe flags are refused unless the local marker is set: "Refuse to serve if dangerous flags are set without the local marker. Prevents a mis-deployed `simulate` / `ALLOW_DEV_ACTOR` from going live." — [apps/pms-core/src/env.ts](../../../../apps/pms-core/src/env.ts)
- Schema migrations: lazy migration in each DO constructor, plus `MigrationSweepWorkflow`, which fans out from the D1 registry to wake cold DOs and report `schema_version`. The trigger route `post_migration_sweep` is `scope: 'dev'` (local only). Pins: `PROPERTY_SCHEMA_HEAD` 58, `ORG_SCHEMA_HEAD` 14, six platform D1 migrations. — [docs/superpowers/specs/2026-07-28-migration-orchestrator-design.md](../../../../docs/superpowers/specs/2026-07-28-migration-orchestrator-design.md); [apps/pms-core/src/v1-dispatch.ts](../../../../apps/pms-core/src/v1-dispatch.ts); [AGENTS.md pins](../../../../AGENTS.md)
- The architecture warns that migration fan-out across thousands of DOs is "real work". Expand/contract is mandatory. — [ARCHITECTURE.md §12](../../../../ARCHITECTURE.md)

**Backups and DR**
- "Per-tenant backup/restore | DO has PITR — but product-level restore tooling is yours to build." — [ARCHITECTURE.md §12](../../../../ARCHITECTURE.md)
- "Backups and DO PITR windows are not covered in Phase 0": a restore to before a shred can recover key material. Every purge certificate carries the limitation `do_pitr_not_covered_phase0`. — [ARCHITECTURE.md §4.8](../../../../ARCHITECTURE.md); [apps/pms-core/src/purge-certificate.ts](../../../../apps/pms-core/src/purge-certificate.ts)
- The R2 event log (NDJSON segments by DO and sequence range) is the "durable event log" and "replay source". — [apps/pms-core/src/event-log.ts](../../../../apps/pms-core/src/event-log.ts); [ARCHITECTURE.md §4.7](../../../../ARCHITECTURE.md)
- No backup, restore or DR runbook, and no restore tooling, was found in the specs or scripts (grep for `backup`/`point-in-time` returned only unrelated hits).

**Purge, erasure and PII**
- Purge is a Workflow over five stores, with keys destroyed first: SHRED_KEYS → PURGE_PROPERTY_DO → PURGE_ORG_DO → PURGE_R2 → PURGE_ICEBERG → VERIFY → CERTIFY. VERIFY can halt the run; certificates are append-only. — [ARCHITECTURE.md §4.8](../../../../ARCHITECTURE.md)
- Shipped workflow steps (org purge): `retention-gate`, `close-traffic`, `shred-keys`, paged `purge-property-do-page-N`, `purge-org-do`, `purge-r2`, `purge-pending-command-open`, `purge-guest-documents-r2`, `skip-iceberg`, `verify`, `certify`. The guest erasure path retains invoice buyer snapshots (`tax_invoice_retention`) and Form C records (`immigration_record_retention`). Iceberg is "out of scope — already skipped". — [apps/pms-core/src/purge-workflow.ts](../../../../apps/pms-core/src/purge-workflow.ts)
- Org lifecycle: `POST /v1/orgs/:id/cancel` (`org:cancel`, action close or reopen) sets status `closing` and `purge_not_before`. `ORG_PURGE_RETENTION_MS = 30 days`. `POST /v1/orgs/:id/purge` (`org:purge`) starts the purge Workflow (202). Guest erasure is `post_guest_erase` (`guests:erase`). — [apps/pms-core/src/v1-dispatch.ts](../../../../apps/pms-core/src/v1-dispatch.ts); [packages/do-runtime/src/platform-migrations.ts](../../../../packages/do-runtime/src/platform-migrations.ts)
- `purge_certificate` table in Platform D1: kind guest or org, `stores_json`, `limitations_json`, `operator_user_id`, outcome certified or halted. — [migrations/d1-platform/0004_purge.sql](../../../../migrations/d1-platform/0004_purge.sql)
- Per-org keys: HKDF-SHA-256 over `orgId` from the platform master key, with separate wrap (`hospai/v1/org-wrap/${orgId}`) and blind-index (`hospai/v1/org-blind/${orgId}`) keys. `data_key.key_version` (0 = legacy, 1 = HKDF). "Master-key rotation UI / rewrap job is out of scope". — [docs/superpowers/specs/2026-09-05-per-org-master-key-hkdf-design.md](../../../../docs/superpowers/specs/2026-09-05-per-org-master-key-hkdf-design.md)
- Events carry `guest_ref` and `pii_key_id`, never plaintext names. Staff, guest, financial and operational data classes have different erasure rules. — [ARCHITECTURE.md §4.8](../../../../ARCHITECTURE.md); [AGENTS.md §1](../../../../AGENTS.md)
- Tenant audit log: an append-only `audit_log` in PropertyDO for money and inventory mutations, readable through `get_audit_log` (by actor, time, shift, reservation). The `audit.append` HTTP route is deliberately not added. — [docs/superpowers/specs/2026-08-07-audit-log-design.md](../../../../docs/superpowers/specs/2026-08-07-audit-log-design.md); [AGENTS.md "Already shipped"](../../../../AGENTS.md)

**Data residency**
- Residency uses `jurisdiction('eu'|'us'|'fedramp')`, which is immutable and part of the DO identity. `locationHint` is latency only, derived from the property timezone. "Never answer a residency question with a location hint." A jurisdictioned DO does not make the request path, TLS or logs regional, so Regional Services are to be priced into enterprise deals. — [ARCHITECTURE.md §4.5](../../../../ARCHITECTURE.md)
- The registry supports only eu, us, fedramp or NULL. India has no Cloudflare DO jurisdiction in this list, so the pilot's PropertyDOs would be non-jurisdictioned with an Asia-Pacific location hint *(inferred from the CHECK constraint and the production resources' Asia-Pacific hints)*. — [migrations/d1-platform/0001_tenant_registry.sql](../../../../migrations/d1-platform/0001_tenant_registry.sql); [docs/roadmap.md Pilot go-live](../../../../docs/roadmap.md)

**Warehouse and analytics (§7.8)**
- Rule: "If a report must tie out to right now or to a closed financial period, it is OLTP. If it is a trend, it is warehouse." Night-audit close-out reports are snapshotted to R2. The Manager Report (R4.32, shipped) is OLTP from snapshots and `availability_day`. No OLTP report may fan out across properties. — [ARCHITECTURE.md §7.8](../../../../ARCHITECTURE.md)
- Planned warehouse: Pipelines → R2 Data Catalog (Iceberg), queried with R2 SQL or DuckDB. It is also the planned cross-tenant fleet-ops and support analytics path ("No tenant PII, no elevation required"). — [ARCHITECTURE.md §4.7, §4.9](../../../../ARCHITECTURE.md)
- No Pipelines or Iceberg binding exists. Purge certificates mark Iceberg `skipped` with `no_iceberg_binding`. A 7-day occupancy trend on the Hub is explicitly not to be built in Phase 1. — [apps/pms-core/src/purge-certificate.ts](../../../../apps/pms-core/src/purge-certificate.ts); [AGENTS.md §4](../../../../AGENTS.md)
