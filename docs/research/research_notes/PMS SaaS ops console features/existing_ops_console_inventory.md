## 2. Specs: decisions and explicit non-goals

### Takeaway
One spec governs the console: `2026-11-22-ops-platform-design.md` (R7.1 §1 to §10, R7.5 §11, R7.3 direction in §12, Clerk amendment in §15). ## 3. Architecture: control plane, operator identity, entitlements, kill-switch, purge, observability

### Takeaway
ARCHITECTURE.md specifies a stricter support-access model than what is built: nobody holds tenant access at rest; READ and WRITE elevation grants are time-boxed, and WRITE needs dual control. The shipped console implements rule 6 (a separate Worker with its own Clerk instance and MFA) and tenant-visible operator actions, but not elevation grants. Fleet analytics are assigned to an Iceberg warehouse that does not exist yet.

### Cited Findings
- §1 names three gating planes plus configuration: Entitlements (Platform D1, "Billing / Revenue" owner), Permissions (OrgDO), **Feature flags** ("Is this code path live?", Engineering, "KV, ephemeral"); the operational kill-switch is a separate fourth signal. — [ARCHITECTURE.md §1, L75-L107](ARCHITECTURE.md)
- §4.9 "Admin & support access": two paths, (1) Iceberg warehouse for fleet analytics, cohort reports, ops dashboards with no tenant PII, (2) a privileged direct DO path for customer support. "Nobody holds tenant access at rest." `ElevationGrant` has `subject`, `mode` READ or WRITE, `reason` (required), `ticketRef` ("required, validated against the helpdesk system"), `requestedBy`, `approvedBy` (required for WRITE, never the requester), `expiresAt` (READ ≤ 60 min, WRITE ≤ 15 min, no renewal). — [ARCHITECTURE.md §4.9, L695-L730](ARCHITECTURE.md)
- §4.9 rules: (1) writes go through the domain; raw SQL is a separate break-glass credential that "automatically opens an incident record"; (2) the tenant sees support access in its own audit log; (3) elevation is internal RBAC in Platform D1, not an entitlement; (4) the kill-switch can void every outstanding grant; (5) elevations are a reviewed weekly metric; (6) "The admin console is a separate Worker (the HospAI Ops Console, `apps/web-admin`) that signs in through its own Clerk instance with a required second factor (amended 2026-11-24) ... bound to nothing a customer-facing Worker can reach. Cloudflare Access in front of it is an optional extra layer." — [ARCHITECTURE.md L732-L752](ARCHITECTURE.md)
- §6.1 Platform D1 entitlement data model includes `entitlement_override (org_id, feature_key, value, reason, granted_by, expires_at)` and `usage_counter`. §6.2 resolution order: plan, add-ons, trial grants (time-boxed), tenant overrides ("sales concessions — always audited"), delinquency policy ("past-due → read-only, not blackout"). — [ARCHITECTURE.md §6.1-§6.2, L946-L969](ARCHITECTURE.md)

### Inferences
- An operator with `ops_admin` holds a standing, non-expiring ability to create customers, change plans and add-ons, suspend and reinstate, and manage operators; the controls on that ability are MFA at sign-in, a reason on each write, the append-only log, tenant visibility of the log, and one global write kill-switch. There is no second-person approval on any shipped operator command, including suspension.
- An operator can indirectly grant tenant access to a person through `ops.add_org_owner` (any signed-up user's email becomes an owner of the org). That action is recorded in `operator_action` and visible to the hotel, but it is a single-operator action; this is the same mechanism the roadmap's "interim support access" could use if not done by the hotel itself. This is my reading of the code paths, not a statement found in the docs.
- The customer list search is a `LIKE` on org name and org id only; there is no search by hotel name, owner email, GSTIN or domain.
- Customer detail shows owners as user ids only, so an operator cannot see who the owners are by name or email from the console.
