# Platform reliability and fleet operations for a Durable-Object-per-tenant SaaS (vendor-side ops console)

Scope: a multi-tenant SaaS on Cloudflare Workers with one SQLite-backed Durable Object (DO) per hotel property and one per organisation, plus Queues, KV, R2 and Workflows. Researched 2026-11-24. Cloudflare figures were read from developers.cloudflare.com on that date; each figure names its page. "Search excerpt only" marks a source whose page I did not open, so treat those lines as lower confidence. Where the notes say "the app must build", that is my inference unless a source is attached.

## 1. Per-tenant schema migrations: rollout, tracking and verification across thousands of per-tenant SQLite stores

### Takeaway
Cloudflare gives no fleet-level schema tooling for Durable Objects: each object owns a private SQLite database and migrates itself in code when it wakes, so the version ledger, the sweep for dormant tenants, and the "tenants by schema version / failed / stuck" view all have to be built by the application. Published database-per-tenant write-ups (Turso, 37signals, Notion) agree on the shape: a version ledger per database, a registry of versions, idempotent append-only migrations, and verification by a different path from the one that did the write.

### Cited Findings
- A Durable Object's storage is private to that object: it "has private, persistent storage that is not shared with other Durable Objects within a namespace", and all objects in a namespace share one class definition. — [Cloudflare DO glossary](https://developers.cloudflare.com/durable-objects/reference/glossary/)
- The only schema pattern Cloudflare's storage API page shows is idempotent `CREATE TABLE IF NOT EXISTS` in the constructor; the page gives no migration or versioning guidance and does not mention PRAGMA support. — [SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- `sql.exec()` "cannot execute transaction-related statements like `BEGIN TRANSACTION` or `SAVEPOINT`"; use `transactionSync()` (callback must be synchronous; a throw rolls the transaction back) or `transaction()`. — [SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- Cloudflare's initialisation pattern is `ctx.blockConcurrencyWhile()` in the constructor: it "ensures no requests are delivered until initialization completes". — [Access Durable Objects storage](https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/)
- `PRAGMA optimize` is supported and "recommended to run ... after a schema change (for example, after creating an index)". — [DO release notes, 2025-02-19](https://developers.cloudflare.com/durable-objects/release-notes/)
- Community sources say `PRAGMA user_version` is not supported in DO SQLite and recommend a migrations table (for example `_sql_schema_migrations`) instead; the `durable-utils` package ships a `SQLSchemaMigrations` class that takes the object's storage and a list of migrations. Search excerpt only, and not confirmed by a Cloudflare page. — [durable-utils README](https://unpkg.com/durable-utils@0.3.5/README.md); [Flavio Copes course page](https://flaviocopes.com/courses/cloudflare/evolve-and-clean-up-objects/)
- The same course page warns that "a migration you've only run on empty objects hasn't been tested" (search excerpt only). — [Flavio Copes course page](https://flaviocopes.com/courses/cloudflare/evolve-and-clean-up-objects/)
- Cloudflare's "Durable Object migrations" are a different thing: they are class lifecycle changes (create, rename, delete, transfer a class), now declared with `exports` (2026-06-30) or the legacy `migrations` array. They are not data-schema migrations. — [Durable Objects migrations](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/); [DO release notes](https://developers.cloudflare.com/durable-objects/release-notes/)
- Enumerating objects: the REST API has `GET /accounts/{account_id}/workers/durable_objects/namespaces/{id}/objects`, returning only `id` and `hasStoredData` per object (no names), paged with a cursor. — [Cloudflare API: list objects](https://developers.cloudflare.com/api/resources/durable_objects/subresources/namespaces/subresources/objects/index.md)
- Cloudflare's architecture guidance says to keep an index instead of waking the fleet: "A parent can be an index and lifecycle manager for a set of children" and "Avoid waking many objects to list, search, or aggregate when an index or analytics service can answer the query." — [DO architecture guidance](https://developers.cloudflare.com/durable-objects/best-practices/architecture-guidance/)
- The same page warns that "multiple instances of the same Durable Object class can share an isolate" and synchronous work in one object "can delay other objects sharing that isolate" (relevant to heavy migrations). — [DO architecture guidance](https://developers.cloudflare.com/durable-objects/best-practices/architecture-guidance/)
- Turso (Jamie Barton, 2025-06-02): database-per-tenant "suddenly turns every schema change into a coordination nightmare". The post contrasts push (server orchestrates every database) with pull (each database reports its version to a registry and applies what it is missing): "The registry is just a versioned catalog of SQL scripts" and "each tenant manages its own updates at its own pace." It gives no failure-tracking or canary tooling. — [Turso: How to deploy schema changes to a million databases](https://turso.tech/blog/how-to-deploy-schema-changes-to-a-million-databases)
- Turso's Multi-DB Schemas feature (a parent schema database whose DDL is pushed to child databases, with DDL blocked in the children) is deprecated for new users (search excerpt only). — [Turso docs: multi-db schemas](https://docs.turso.tech/features/multi-db-schemas)
- 37signals (Mike Dalessio, 2026-02-13): the `activerecord-tenanted` gem gives each tenant its own SQLite file; creating a tenant "applied all of the schema migrations"; guards raise on a missing tenant, on a tenanted model used with no tenant set, and on a write whose tenant does not match the connection. Fizzy did not launch on SQLite-per-tenant because of unfinished replication and failover edge cases; it launched on MySQL. The page does not say whether existing tenants migrate at deploy or on access. — [37signals: Rails multi-tenancy](https://dev.37signals.com/rails-multi-tenancy/)
- Notion (Garrett Fidalgo, 2021-10-06): 480 logical shards across 32 physical databases; migration by double-write, backfill that "compare[s] record versions" before writing, verification by a sampling script plus "dark" reads; migration and verification were written by different people to avoid "making the same error in both stages". — [Notion: Herding elephants](https://www.notion.com/blog/sharding-postgres-at-notion)
- Azure's multitenant guidance states the reporting requirement directly: "You need to know which version of infrastructure, software, or feature each tenant uses, what they're eligible to migrate to, and the time-based data associated with those states. Tracking this information is often one of the responsibilities of a control plane." — [Azure Architecture Center: updates in multitenant solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/updates)
- Bytebase lists "keeping track of schema versions across many tenant databases" as a core cost of the database-per-tenant model (search excerpt only). — [Bytebase: multi-tenant database patterns](https://www.bytebase.com/blog/multi-tenant-database-architecture-patterns-explained/)

### Inferences
- Lazy migrate-on-access is the natural default for DOs (the object must be awake to touch its own SQLite), but it leaves dormant tenants on old versions indefinitely. A fleet sweep is still needed before old migration code or old-schema compatibility can be removed, and to find broken tenants before the customer does.
- The fleet view the console needs, none of which Cloudflare provides:
  - Tenants by schema version (histogram against the current head), for property objects and organisation objects separately.
  - Failed migrations: tenant, from-version, to-version, error, attempt count, first and last failure time, code version that attempted it.
  - Stuck tenants: below head for longer than N days, or not woken since the release.
  - Per-tenant migration history (version, applied-at, duration, code version).
  - Sweep job state: target version, batch size, progress, paused or running, failures.
- The version ledger has to live in two places: inside each DO (the source of truth, written in the same transaction as the migration) and in a control-plane registry (reported on wake or on migration, used for the fleet view). The REST list endpoint cannot substitute for the registry because it returns hex IDs without names or versions.
- Operator actions that follow: "migrate this tenant now" (wake and report), "run sweep" (dry run, canary, batches), "retry failed", "quarantine tenant" (block writes while its schema is in doubt), and "verify" (a schema fingerprint read from `sqlite_master` compared with the expected one).
- A migration runs inside one object's CPU budget (30 s default, 5 min configurable, see section 5) and blocks that tenant's requests while it runs, so large data rewrites need chunking (for example alarm-driven steps) rather than one constructor call.
- A guard worth having: if the stored schema version is higher than the code's known head (after a code rollback), the object should fail closed on writes rather than run old code against a newer schema.

### Gaps
- No official Cloudflare page on data-schema migration strategy across many Durable Objects was found; the `PRAGMA user_version` limitation is from community sources only.
- No published write-up was found of an operator running schema migrations across a very large Durable Object fleet with numbers (failure rates, sweep duration).
- PlanetScale, Neon (branch per tenant) and Fly.io LiteFS material was not reviewed in this pass.
- The 37signals page does not state when existing tenant databases are migrated; the gem README would need reading.

## 2. Backup, point-in-time recovery and restore per tenant

### Takeaway
Every SQLite-backed Durable Object has point-in-time recovery for the past 30 days, callable only from code inside that object, restoring the whole database (SQL and key-value data) of that one object and nothing else; a restore can be undone with the bookmark returned by the restore call. There is no documented export, clone or fork API and no backup beyond 30 days, so tenant export, longer retention, restore-to-a-copy and every safeguard around "restore property to bookmark" are application work.

### Cited Findings
- PITR is available on SQLite-backed objects "to restore a Durable Object's embedded SQLite database to any point in time in the past 30 days. These methods apply to the entire SQLite database contents, including both the object's stored SQL data and stored key-value data using the key-value `put()` API." — [SQLite storage API: PITR](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- "The PITR API is not supported in local development because a durable log of data changes is not stored locally." — [SQLite storage API: PITR](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- Bookmarks are "mostly alphanumeric" strings that are "lexically comparable: a bookmark representing an earlier point in time compares less than one representing a later point". — [SQLite storage API: PITR](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- API surface, all on `ctx.storage` (inside the object): `getCurrentBookmark()`; `getBookmarkForTime(timestamp)` (approximate point, "must be within the last 30 days"); `onNextSessionRestoreBookmark(bookmark)`, which makes the object restore on its next restart, after which "the application should typically invoke `ctx.abort()` to restart the Durable Object". — [SQLite storage API: PITR](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- Undo: `onNextSessionRestoreBookmark` "returns a special bookmark representing the point in time immediately before the recovery takes place ... after the recovery completes, it can be undone by performing a second recovery to this bookmark." — [SQLite storage API: PITR](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- PITR is "on by default for all SQLite-backed DOs"; it works by replaying the change log from the last snapshot, and logs are kept for 30 days. Changes are uploaded to object storage in batches (every 10 seconds or 16 MB), each committed transaction goes to five followers in different data centres and needs three acknowledgements. The post describes PITR as "an accidental feature that fell out of SRS's design". — [Cloudflare blog: Zero-latency SQLite storage in every Durable Object](https://blog.cloudflare.com/sqlite-in-durable-objects/)
- New Durable Object namespaces must use the SQLite backend (2026-07-09) unless the account already has a KV-backed namespace; only SQLite-backed objects have PITR. — [Changelog 2026-07-09](https://developers.cloudflare.com/changelog/post/2026-07-09-restrict-new-kv-backed-namespaces/)
- `deleteAll()` on a SQLite-backed object "removes the entire contents" (SQL and KV) atomically; with compatibility date 2026-02-24 or later it also deletes the active alarm. — [SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- `ctx.storage.sql.databaseSize` returns "the current SQLite database size in bytes". — [SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- The only export guidance found is in the architecture page: older time-bucket objects "can be exported to R2 and deleted" (an application pattern, not a platform feature). — [DO architecture guidance](https://developers.cloudflare.com/durable-objects/best-practices/architecture-guidance/)
- Data Studio can read and write one object's SQL data from the dashboard (see section 3), which is a manual repair path, not a backup. — [Data Studio](https://developers.cloudflare.com/durable-objects/observability/data-studio/)
- Workflows keep completed instance state for 3 days (Free) or 7 days by default, configurable up to 30 days (Paid); queue messages are kept up to 14 days. Neither is a backup of tenant data. — [Workflows limits](https://developers.cloudflare.com/workflows/reference/limits/); [Queues limits](https://developers.cloudflare.com/queues/platform/limits/)

### Inferences
- Restoring one tenant does not touch other tenants at the storage level, because PITR is scoped to one object. The risk is logical: a property object restored to an earlier time is now behind everything that was derived from it or coordinated with it.
- Safeguards an operator action "restore property to bookmark" needs:
  - Must be an RPC on the object itself (the API exists only on `ctx.storage`), called through the app's own authorised operator route.
  - Capture `getCurrentBookmark()` and the bookmark returned by the restore call, and store both outside the restored object. Anything written inside the object, including an in-object audit log, is rolled back by the restore.
  - Typed confirmation naming the tenant, a mandatory reason or ticket, a second approver for production, and an audit record in a separate store.
  - A preview step: the target time, the resolved bookmark, and what will be lost (writes between target and now: count of reservations, folio postings, payments, night-audit runs).
  - Put the tenant in maintenance or read-only mode first, and pause that tenant's queue consumers and scheduled work until reconciliation is done.
  - Reconciliation list for state outside the object that PITR does not rewind: outbox events already delivered to Queues, KV projections, R2 documents, Workflows instances, the organisation object (guest vault, keys), other properties' objects, and third parties (payment gateway, channel manager, tax or police filings). A restore can leave captured payments with no folio row, or idempotency keys forgotten so that a replayed command executes twice.
  - Schema version: the restored database may be at an older schema, so forward migrations must run on wake before requests are served.
  - An "undo restore" action using the saved pre-restore bookmark, valid inside the same 30-day window.
  - A drill: PITR does not work in local development, so restore has to be rehearsed on staging.
- Whether alarm state is rewound by PITR is not documented; the action should explicitly re-arm the object's alarm after restore.
- 30 days is a recovery window, not a retention policy. Contractual or legal retention, and "give this hotel its data" requests, need an application export (per-tenant dump to R2) on a schedule, with its own restore test.
- Because no clone or fork API is documented, "restore to a copy and compare" (the safer pattern on conventional databases) has to be built as export from the source object and import into a scratch object.
- Bookmarks are per object, so restoring an organisation and its properties to "the same moment" means resolving `getBookmarkForTime` separately in each object; the result is only approximately consistent across objects.

### Gaps
- Not documented: whether alarms are restored by PITR; whether the 30-day window can be extended; whether PITR history survives `deleteAll()` or class deletion; any cost for PITR itself; any API to restore from outside the object or to list bookmarks.
- No Cloudflare-published runbook for PITR on a multi-object tenant was found.
- KV and R2 backup features (for example R2 versioning or bucket locks) were not checked in this pass.

## 3. Observability per tenant

### Takeaway
Cloudflare now exposes per-instance signals (logs and traces carry the Durable Object ID, the dashboard can filter namespace metrics to one object, Data Studio can query one object's SQLite), but it does not give a tenant-labelled fleet view: storage is charted per namespace only, the list API returns unnamed IDs, log retention is 7 days, and nothing knows what a "tenant" is. Tenant error rates, latency, storage size, request volume and alarm failures need tenant context emitted by the application and a tenant registry to join against.

### Cited Findings
- Workers Logs and OpenTelemetry spans for Durable Object requests include the instance ID: "Use `$workers.durableObjectId` to filter logs for a specific instance. Root and child spans include the same ID in `cloudflare.durable_object.id`." — [Durable Objects changelog](https://developers.cloudflare.com/changelog/product/durable-objects/)
- Durable Object logs are "aggregated by the script name and the Durable Object class name"; namespace metrics come from the GraphQL Analytics API (default window 24 hours); the dashboard can filter to one object by ID or name. Datasets: `durableObjectsInvocationsAdaptiveGroups`, `durableObjectsPeriodicGroups`, `durableObjectsStorageGroups`, `durableObjectsSubrequestsAdaptiveGroups`. — [DO metrics and analytics](https://developers.cloudflare.com/durable-objects/observability/metrics-and-analytics/)
- Memory is per isolate, not per object: "The chart always reports the memory of the whole isolate, not an individual Durable Object." Each isolate has a 128 MB limit. — [DO metrics and analytics](https://developers.cloudflare.com/durable-objects/observability/metrics-and-analytics/)
- Total SQLite storage is charted per namespace (maximum per hour) since 2026-07-20: "Viewing storage for individual Durable Objects by ID or name is not supported." — [Changelog 2026-07-20](https://developers.cloudflare.com/changelog/post/2026-07-20-durable-objects-total-storage-metrics/)
- Inside an object, `ctx.storage.sql.databaseSize` returns the database size in bytes. — [SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- `ctx.id.name` (2026-03-15) and `ctx.id.jurisdiction` (2026-03-26) are available inside the object, so it can label its own telemetry without the name being passed in. — [Durable Objects changelog](https://developers.cloudflare.com/changelog/product/durable-objects/); [Durable Object ID](https://developers.cloudflare.com/durable-objects/api/id/)
- Data Studio: view and write one SQLite-backed object's data from the dashboard, selected by "an object's unique name or ID"; SQL data only (KV-API data "will be made read-only in the future"); queries hit the live object and "incur usage billing for requests, duration, rows read, and rows written"; every query is audit logged as "query executed" and "query completed" events sharing a `query_id`. — [Data Studio](https://developers.cloudflare.com/durable-objects/observability/data-studio/)
- Data Studio status and role conflict between sources: the launch changelog (2025-10-16) labels it Beta and requires the `Workers Platform Admin` role; the current docs page (updated 2026-09-15) does not state beta or GA and requires "at least `Editor` access to the Worker that implements the Durable Object". — [Changelog 2025-10-16](https://developers.cloudflare.com/changelog/post/2025-10-16-durable-objects-data-studio/); [Data Studio](https://developers.cloudflare.com/durable-objects/observability/data-studio/); [DO roles and permissions](https://developers.cloudflare.com/workers/authorization/durable-objects/)
- `Metadata Read-Only` access to the Worker "includes Durable Object metrics, logs, and traces without granting access to data stored in the Durable Object". — [DO roles and permissions](https://developers.cloudflare.com/workers/authorization/durable-objects/)
- REST list of objects in a namespace returns `id` and `hasStoredData` only. — [Cloudflare API: list objects](https://developers.cloudflare.com/api/resources/durable_objects/subresources/namespaces/subresources/objects/index.md)
- A `DurableObjectId` "will be logged outside of the specified jurisdiction for billing and debugging purposes". — [DO data location](https://developers.cloudflare.com/durable-objects/reference/data-location/)
- Workers Logs: retention 3 days (Free) and 7 days (Paid); 5 billion logs per account per day, then 1% head sampling; 256 KB maximum log size; JSON logs have fields extracted and indexed; Paid includes 20 million events per month then $0.60 per million; alarm invocations are logged. The page states Workers Logs moves to Cloudflare Observability pricing on 2026-12-01. — [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)
- Workers observability features listed: Workers Logs, Query Builder (filters, aggregations, groupings), traces and OpenTelemetry export, Logpush (to R2, S3 or providers), Tail Workers (custom filtering, sampling, transformation), real-time logs, metrics, "Issues" (groups recurring failures and routes them to webhooks, chat or incident tools), source maps. — [Workers observability](https://developers.cloudflare.com/workers/observability/)
- Workers Analytics Engine limits: 250 data points per invocation; 20 blobs, 20 doubles and 1 index per data point; 16 KB total blob size; index up to 96 bytes; "stored for three months". — [Analytics Engine limits](https://developers.cloudflare.com/analytics/analytics-engine/limits/)
- A Deployments tab on each Durable Object namespace (2026-08-20) shows live versions with traffic share, requests per second, error rate and median wall time per version; it is read-only. — [Changelog 2026-08-20](https://developers.cloudflare.com/changelog/post/2026-08-20-durable-objects-deployments-tab/)
- Alarms: "guaranteed at-least-once execution and will be retried upon failure using exponential backoff, starting at 2 second delays for up to 6 retries"; after that the alarm does not run again "until the next time you call `setAlarm`". The handler receives `retryCount` and `isRetry`. — [DO alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)
- AWS SaaS Lens: "SaaS providers need to be able to view system activity and health through the lens of individual tenants and tenant tiers." — [AWS SaaS Lens: tenant-aware operations](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/tenant-aware-operations.html)
- AWS SaaS Lens OPS 1: "Include a tenant identifier and, if possible, a user-friendly tenant name in log messages"; "Make tenant and tenant attributes first-class citizens in the operational experience"; "Configure alerts and alarms that are triggered when tenants reach specific health states or performance thresholds." — [AWS SaaS Lens OPS 1](https://wa.aws.amazon.com/saas.question.OPS_1.en.html)

### Inferences
- What Cloudflare gives without application work: namespace-level request, CPU, subrequest and storage charts; per-object filtering in the dashboard when the ID or name is known; logs and traces filterable by Durable Object ID; one-object data inspection in Data Studio with audit logging; per-version error rates during a rollout.
- What is missing for a vendor console: a list of tenants with health; storage size per tenant; error rate and latency per tenant over time (logs keep 7 days); alarm-exhaustion detection (after 6 retries an alarm silently stops); mapping from a hex object ID back to a tenant; any view an operator without Cloudflare dashboard access can use.
- A workable design from the documented parts:
  - Emit one Analytics Engine data point per request or command with the tenant ID as the index and outcome, route or command, duration, and error code as blobs and doubles. Retention is three months, and the 250-points-per-invocation limit bounds the detail.
  - Log structured JSON with tenant ID, organisation ID, object name and version so the Query Builder can group by tenant; use Logpush to R2 if more than 7 days is needed.
  - Have each object report `databaseSize`, row counts for its largest tables, schema version, next alarm time and last alarm outcome to the registry on a schedule (a heartbeat), since no platform view has these per object.
  - Record alarm failures in the object (catch in `alarm()`, persist, re-arm) and surface "alarm overdue" in the console: next alarm time in the past by more than a threshold.
- Data Studio is a useful break-glass tool for engineers but a poor support tool: it needs Cloudflare account roles, it runs against live production objects, it can write, and its audit trail is in Cloudflare's audit log rather than the product's own operator audit log. Read-only, tenant-scoped, PII-aware inspection belongs in the app's console.
- Memory charts cannot attribute pressure to a tenant because isolates are shared between objects of the same class.

### Gaps
- GraphQL dimensions for per-object queries (for example an `objectId` dimension) are not stated on the metrics page; it recommends schema introspection. Not verified.
- The Workers Logs page did not say what the Cloudflare Observability pricing from 2026-12-01 will be; not checked further.
- Whether Data Studio works for jurisdiction-restricted objects is not stated.
- No platform alert for "an alarm exhausted its retries" was found.

## 4. Queues and async work: dead letters, replay, backlog, Workflows, failing alarms

### Takeaway
Cloudflare Queues give dead-letter queues, configurable retries and delays, pause and purge, and backlog metrics, but no documented way to browse or filter messages by tenant and no built-in redrive, so "show this tenant's backlog" and "replay these failed messages" need application tables and consumers. Workflows have per-instance status, pause, resume, restart, terminate and delete. Alarms stop after six failed retries unless the handler catches and re-arms.

### Cited Findings
- A dead-letter queue is set per consumer; messages go there after `max_retries` (default 3). "Without a DLQ configured, messages that reach the retry limit are deleted permanently." A DLQ "is like any other queue" and needs its own consumer; "Messages delivered to a DLQ without an active consumer will persist for four (4) days before being deleted". The DLQ must be in the same jurisdiction as its source queue. — [Queues: dead letter queues](https://developers.cloudflare.com/queues/configuration/dead-letter-queues/)
- A failed message in a batch causes the whole batch to be retried unless messages are explicitly acknowledged; `retry()` and `retryAll()` accept a delay; `retry_delay` sets a default per consumer. — [Queues: batching, retries and delays](https://developers.cloudflare.com/queues/configuration/batching-retries/)
- Queues limits: max retries 100; retention up to 14 days (24 hours on Free); message size 128 KB; 5,000 messages per second per queue; batch up to 100 messages; 250 concurrent consumer invocations; consumer wall time 15 minutes; max delay 24 hours; backlog 25 GB per queue; 10,000 queues per account by default. — [Queues limits](https://developers.cloudflare.com/queues/platform/limits/)
- Pause and purge: delivery can be paused and resumed (the queue keeps accepting messages, which still expire at the retention period); purge "permanently deletes" all messages and is irreversible. Available in Wrangler, REST API and dashboard. — [Queues: pause and purge](https://developers.cloudflare.com/queues/configuration/pause-purge/)
- Queue metrics: backlog bytes and messages (`queuesBacklogAdaptiveGroups`), consumer concurrency (`queueConsumerMetricsAdaptiveGroups`), message operations with `lagTime`, `retryCount` and outcome `success`, `dlq` or `fail` (`queueMessageOperationsAdaptiveGroups`); realtime `backlog_count`, `backlog_bytes` and `oldest_message_timestamp_ms` via REST and JavaScript APIs. No per-message listing is described on the page. — [Queues metrics](https://developers.cloudflare.com/queues/observability/metrics/)
- Pull consumers can pull and acknowledge up to 5,000 messages per second per queue over HTTP. — [Queues changelog](https://developers.cloudflare.com/queues/platform/changelog/)
- Workflows instance API: `status()`, `pause()`, `resume()`, `restart()` ("from the beginning, or from a specific step"), `terminate()` (optionally `{ rollback: true }` to run registered rollback handlers; a terminated instance cannot be resumed), `delete()`, `subscribe()`. Status values: `queued`, `running`, `paused`, `errored`, `terminated`, `complete`, `waiting`, `waitingForPause`, `unknown`, with `error` and a `rollback` outcome. — [Workflows Workers API](https://developers.cloudflare.com/workflows/build/workers-api/); [Trigger Workflows](https://developers.cloudflare.com/workflows/build/trigger-workflows/)
- Workflows limits (Paid): 50,000 concurrent instances per account; 300 creations per second per account and 100 per Workflow; 10,000 steps by default, configurable to 25,000; completed-instance retention 7 days by default, up to 30; 1 GB persisted state per instance; 1 MiB per step result and per event payload; `step.sleep` up to 365 days; 2,000,000 queued instances. — [Workflows limits](https://developers.cloudflare.com/workflows/reference/limits/)
- Per-Workflow concurrency limits queue the excess rather than reject it; `waiting` and `paused` instances do not count. — [Workflows concurrency limits](https://developers.cloudflare.com/workflows/build/concurrency-limits/)
- Retention can be set per instance at creation (`successRetention`, `errorRetention`). — [Workflows Workers API](https://developers.cloudflare.com/workflows/build/workers-api/)
- Alarms: one alarm per object; at-least-once; up to 6 retries from a 2-second backoff. Cloudflare recommends "to catch any exceptions inside your `alarm()` handler and schedule a new alarm before returning if you want to make sure your alarm handler will be retried indefinitely", because otherwise "a sufficiently long outage in a downstream service ... or a bug in your code that goes unfixed for hours can exhaust the limited number of retries". — [DO alarms](https://developers.cloudflare.com/durable-objects/api/alarms/)
- `ctx.abort(reason, { retryAlarm: false })` (2026-08-25) stops an in-progress alarm from retrying after an abort; the default still retries. — [Changelog 2026-08-25](https://developers.cloudflare.com/changelog/post/2026-08-25-durable-object-alarm-abort-no-retry/)
- If the account hits its Durable Objects spending cap, objects are blocked ("Exceeded the account's spending cap for Durable Objects") and the troubleshooting page says to "review alarm recovery before resuming". — [DO troubleshooting](https://developers.cloudflare.com/durable-objects/observability/troubleshooting/)

### Inferences
- A tenant's outbox or backlog is only inspectable if the outbox is a table inside the tenant's object (pending, delivered, failed, attempts, last error). Shared queues carry all tenants' messages and the platform offers counts, not contents.
- Console functions that follow:
  - Queue health per queue: backlog count, oldest message age, retry rate, DLQ arrival rate, paused or running; actions pause and resume. Purge should be withheld from the console or put behind a strong confirmation because it affects every tenant on the queue.
  - Dead-letter browser: needs a DLQ consumer that persists each failed message with tenant ID, event type, error, attempts and first-seen time into a queryable store. Without that consumer, DLQ messages expire after 4 days.
  - Replay: selected messages, all for a tenant, or all for an event type; replay must go back through the normal consumer path so permission, entitlement and idempotency checks still apply; show a dry-run count first.
  - Per-tenant outbox view: pending and failed events, age of the oldest, "re-emit" action.
  - Workflow instance list filtered by tenant (needs the tenant ID in the instance ID or in an app index, since instances are looked up by ID), with status, current step, error, and pause, resume, restart-from-step, terminate actions.
  - Alarm watchdog: objects whose next alarm is overdue or whose last alarm failed; action "re-arm alarm".
- `max_retries` up to 100 combined with a `retry_delay` gives a long outage tolerance for third-party integrations before messages dead-letter; the 14-day retention is the outer bound.
- Because completed Workflow state is kept at most 30 days, any audit need beyond that (for example a purge certificate) must be written to the app's own store before the instance expires.

### Gaps
- No documented redrive from a DLQ back to its source queue, and no documented way to peek at messages without consuming them, was found on the pages read. A pull consumer on the DLQ may serve as a peek, but that was not verified.
- Whether Workflows instances can be listed and filtered by status through the binding (as opposed to the REST API and Wrangler) was not confirmed.
- Queues event subscriptions and any Cloudflare alerting on DLQ depth were not checked.

## 5. Noisy neighbour, limits and quotas

### Takeaway
The per-tenant object is also the isolation boundary: each object is single-threaded with a soft limit of 1,000 requests per second, 10 GB of SQLite storage on Workers Paid, and 30 seconds of CPU per invocation (configurable to 5 minutes). Hitting the storage limit makes the tenant read-only in effect (writes fail, reads and deletes work). Cloudflare's rate-limit binding is approximate and per location, so strict per-tenant quotas and any usage metering for billing are application concerns.

### Cited Findings
- "Each SQLite-backed Durable Object has a storage limit of 10 GB on a Workers Paid plan"; "There are no limits for storage per account when using SQLite-backed Durable Objects on a Workers Paid plan"; Free plan objects are limited to 1 GB each and 5 GB per account. Storage is measured in GB of 1,000,000,000 bytes. — [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/); [DO FAQ](https://developers.cloudflare.com/durable-objects/reference/faq/)
- At the storage limit, writes fail with `database or disk is full: SQLITE_FULL`; "Read operations ... will continue to work, and `DELETE` operations will also succeed". — [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/)
- "An individual Object has a soft limit of 1,000 requests per second. You can have an unlimited number of individual objects per namespace." An overloaded object returns an overloaded error to the caller. — [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/)
- CPU per request is 30 seconds by default, configurable to 5 minutes with `limits.cpu_ms`; each incoming request or WebSocket message resets the budget. Alarm handler wall time is 15 minutes. Key plus value in the KV API is 2 MB; 100 bound parameters per SQL query; 100 columns per table; 6 simultaneous outgoing connections per request; received WebSocket messages up to 32 MiB. — [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/); [DO architecture guidance](https://developers.cloudflare.com/durable-objects/best-practices/architecture-guidance/)
- Overload errors: "Durable Object is overloaded. Too many requests queued.", "Too much data queued.", "Requests queued for too long.", "Too many requests for the same object within a 10 second window." Account-level: "Your account is generating too much load on Durable Objects. Please back off and try again later." and "Your account is doing too many concurrent storage operations." — [DO troubleshooting](https://developers.cloudflare.com/durable-objects/observability/troubleshooting/)
- Errors carry `.retryable` and `.overloaded`; "Errors with the property `.overloaded` set to True should not be retried. If a Durable Object is overloaded, then retrying will worsen the overload". After an exception the stub may be broken and should be recreated. — [DO error handling](https://developers.cloudflare.com/durable-objects/best-practices/error-handling/)
- Isolates are shared: synchronous work in one object "can delay other objects sharing that isolate"; a sign of a boundary that is too coarse is "One customer's spike slows down other customers." For append-only data nearing 10 GB, Cloudflare recommends time-bucket objects (for example `audit:{tenantId}:{yyyy-mm}`) exported to R2 and deleted. — [DO architecture guidance](https://developers.cloudflare.com/durable-objects/best-practices/architecture-guidance/)
- SQLite storage billing for Durable Objects began in January 2026 (target date 2026-01-07). — [SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/); [DO release notes](https://developers.cloudflare.com/durable-objects/release-notes/)
- Rate Limiting binding: `limit({ key })` with `simple.limit` and `simple.period` ("Must be either 10 or 60" seconds); keys such as "user IDs and tenant IDs" are recommended; "Rate limits are approximate and apply separately in each Cloudflare location"; "Requests can exceed your configured limit while counts update in the background"; for one strict global limit the page recommends building a limiter with Durable Objects. — [Rate Limiting binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)
- Workers Logs and Analytics Engine volume limits that a tenant can exhaust: 5 billion logs per account per day then 1% sampling; 250 Analytics Engine data points per invocation. — [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/); [Analytics Engine limits](https://developers.cloudflare.com/analytics/analytics-engine/limits/)
- Azure notes that with multitenant stamps "the noisy neighbor problem still might occur" (search excerpt only). — [Azure: Deployment Stamps pattern](https://learn.microsoft.com/azure/architecture/patterns/deployment-stamp)

### Inferences
- A tenant cannot directly starve another tenant's object of its single thread, but tenants do share: isolates (CPU and the 128 MB memory limit), the stateless Worker in front, queues and their consumers, account-level rate and storage-operation limits, KV and R2 namespaces, and the account's bill.
- Console functions that follow:
  - Storage headroom per tenant (from the heartbeat in section 3) with warning thresholds well below 10 GB, since at the limit the property stops accepting writes. A hotel property is unlikely to reach 10 GB from transactional rows alone; audit logs and event history are the usual growth, hence the time-bucket guidance.
  - Top-N tenants by requests, CPU time, queue messages produced, errors and storage; overload and `SQLITE_FULL` error counts per tenant.
  - Per-tenant throttles an operator can set or lift (API rate, bulk import rate, report generation), with the reason and expiry recorded.
  - Quota view per plan: rooms, users, properties, API calls, storage, with current usage.
- Usage metering for billing has to be built: Cloudflare bills the account, not the tenant. The object is the natural meter (counts kept transactionally), with periodic export to the billing system; Analytics Engine is suitable for trends but is not described as exact, so it should not be the billing ledger.
- The rate-limit binding suits abuse protection at the edge; contractual quotas ("N API calls per month") need a strict counter, which the tenant's own object can hold.

### Gaps
- Whether Analytics Engine applies sampling at high volume was not stated on the limits page read; not verified.
- KV and R2 per-namespace limits and rate limits were not checked.
- No Cloudflare feature for per-tenant cost attribution inside one account was found on the pages read.

## 6. Kill switches and degraded modes

### Takeaway
Cloudflare supplies primitives (a feature-flag service called Flagship with a Workers binding, queue pause, Workflow pause, and the storage-full behaviour that leaves reads working), but per-tenant and global kill switches, read-only mode, maintenance mode and integration circuit breakers are application features. Vendor guidance on kill switches is consistent: they are permanent operational controls, they default to "feature on", they must fail safe when the flag system is unreachable, and each toggle should alert and be audited.

### Cited Findings
- "Flagship is Cloudflare's feature flag service": flags are evaluated through a native Workers binding with "automatic fallback to defaults" or through OpenFeature SDKs; targeting rules "Serve different flag values based on user attributes" with 13 comparison operators and AND/OR grouping; percentage rollouts use consistent hashing. The page does not state beta or GA, pricing, or audit history. — [Cloudflare Flagship](https://developers.cloudflare.com/flagship/)
- Queue delivery can be paused per queue while the queue keeps accepting messages. — [Queues: pause and purge](https://developers.cloudflare.com/queues/configuration/pause-purge/)
- Workflow instances can be paused and resumed individually. — [Workflows Workers API](https://developers.cloudflare.com/workflows/build/workers-api/)
- A full object degrades to read-and-delete only (`SQLITE_FULL`). — [DO limits](https://developers.cloudflare.com/durable-objects/platform/limits/)
- Azure: "Where appropriate, isolate volatile integrations behind internal interfaces, and define fallback or degraded behavior for outages and incompatible changes." — [Azure: updates in multitenant solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/updates)
- Azure on maintenance windows: "Outage windows are generally considered an outdated practice for software as a service", though a regular maintenance window can still be defined to tell customers when changes happen. — [Azure: updates in multitenant solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/updates)
- Keleher on automatic switches: turn off the new system when its error count rises, before an engineer has to intervene, and keep rollouts easy to disable. — [Backfills should fail in minutes, not days](https://will-keleher.com/posts/backfills-should-fail-in-minutes-not-days/)
- Google SRE on speed of mitigation: requiring a person to approve routine failover adds delay without adding safety; "Decoupling operator from operation is very powerful." — [Google SRE book: automation](https://sre.google/sre-book/automation-at-google/)
- Kill-switch guidance (all search excerpt only): a kill switch's default should be "feature on" and, being permanent, it is coded differently from temporary flags (Spotify Confidence); the fallback value should keep the feature on so a connectivity problem does not switch it off (Datadog); the application should keep running if the flag system fails (Unleash); maintenance mode needs admin bypass and operational control separate from user access (ConfigCat); maintenance mode can be targeted per user or segment without a restart (LaunchDarkly); alert when a kill switch is toggled (Statsig). — [Spotify Confidence glossary](https://confidence.spotify.com/glossary/kill-switch); [Datadog: kill switches](https://docs.datadoghq.com/feature_flags/use_cases/kill_switches/); [Unleash: feature flag best practices](https://docs.getunleash.io/guides/feature-flag-best-practices); [ConfigCat](https://configcat.com/blog/biggest-blunder-in-feature-flag-history/); [LaunchDarkly: rolling maintenance modes](https://launchdarkly.com/blog/how-launchdarkly-uses-feature-flags-for-rolling-maintenance-modes/); [Statsig: kill switches](https://statsig.com/perspectives/kill-switches-in-software-development)

### Inferences
- A useful taxonomy for the console, by scope and effect:
  - Global: disable a feature or integration everywhere; global read-only; global maintenance page.
  - Per tenant (organisation or property): suspend (billing or abuse), read-only (during restore, repair or migration), maintenance (operator working on it), feature off for this tenant only.
  - Per integration: circuit breaker for a payment gateway, channel manager, messaging or tax interface, global or per tenant, with manual open and close plus automatic open on error rate.
  - Per workload: pause a queue consumer, a scheduled job (night audit), or a Workflow class.
- Where the switch state lives matters for a money and inventory system: a switch that gates writes inside a tenant's object should be read inside the object's transaction (strongly consistent), not from an eventually consistent store. Flags that only shape the stateless Worker's behaviour can come from Flagship or KV. This is my inference; the read pages do not address it.
- Each switch needs: who may toggle it, a mandatory reason, an optional expiry (auto-revert), a visible banner for affected users, an alert to the on-call channel, an audit entry with before and after values, and a list on the console home of every switch currently not in its default state.
- Switches must exempt what cannot stop: legal duties (erasure, statutory filings), security actions and the operator's own access. A global lifecycle kill switch should explicitly say whether it blocks destructive tenant operations such as cancel and purge.
- Read-only mode should be a first-class state that every write path checks, with one error code and one user-facing message, because it is the precondition for restore (section 2), tenant copy (section 9) and repair (section 7).

### Gaps
- Flagship's maturity (beta or GA), pricing, per-tenant targeting on arbitrary context, change history and propagation delay are not stated on the page read.
- No authoritative source was found for per-tenant read-only mode design or for auditing switch toggles; the vendor posts above are marketing-adjacent and were not opened.

## 7. Incident tooling: impact lists, customer communication, fleet-wide repair

### Takeaway
"Which tenants were affected" can only be answered if telemetry is keyed by tenant; status tooling (Atlassian Statuspage audience-specific pages, incident.io customer status pages) can then target updates to those customers. For post-incident repair across many tenants, the published guidance converges on: run on a subset first, make the job idempotent, iterate by key, control the rate at run time, verify by a separate path, and build in sanity checks and automatic stops; Google's Diskerase incident is the standard warning about automation that treats an empty selector as "everything".

### Cited Findings
- Atlassian Statuspage audience-specific pages target updates "only to those customers impacted by an incident" without a separate page per group (search excerpt only). — [Atlassian Statuspage: audience-specific pages](https://www.atlassian.com/software/statuspage/audience-specific-pages)
- incident.io customer status pages are authenticated, per-customer pages managed centrally; one update goes only to impacted customers; access can be granted by email domain (search excerpt only). — [incident.io: customer status pages](https://incident.io/changelog/customer-status-pages)
- An Adobe community thread notes that incidents found by internal monitoring may not be known "at a granular level", so a precise affected-customer list may not exist (search excerpt only). — [Adobe Experience League thread](https://experienceleaguecommunities.adobe.com/adobe-real-time-customer-data-platform-25/incidents-message-impact-scope-some-customers-are-impacted-144526)
- Cloudflare "Issues" groups recurring Worker failures and routes them to webhooks, chat services or incident-management tools. — [Workers observability](https://developers.cloudflare.com/workers/observability/)
- Azure: "ensure that you have a process to monitor the health of your tenants, especially before and after updates are applied. Critical production incidents ... often occur after changes to code or configuration." — [Azure: updates in multitenant solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/updates)
- Azure on support visibility: support staff should be able to answer "Have updates recently been applied to a tenant's infrastructure or to shared components? What was the nature of those updates? What was the previous version? How frequently are updates applied to this tenant?" — [Azure: updates in multitenant solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/updates)
- Google SRE, Diskerase: an empty set was treated as meaning "everything"; "Within minutes, the highly efficient Diskerase wiped the disks on all machines in our CDN." - Google SRE: "Automation needs to be careful about relying on implicit" safety signals; non-idempotent fixes on a retry loop "might render the system in an inconsistent state"; "the value of consistency is in many ways the primary value of automation"; "a bug fixed in the code will be fixed there once and forever." — [Google SRE book: automation](https://sre.google/sre-book/automation-at-google/)
- Google SRE, toil: work that is manual, repetitive, automatable, tactical, without enduring value, and that scales linearly with service growth; the stated goal is to keep it "below 50% of each SRE's time"; engineering "enables the SRE organization to scale up sublinearly with service size." — [Google SRE book: eliminating toil](https://sre.google/sre-book/eliminating-toil/)
- Keleher on backfills: "do the migration/backfill on only a subset of your data so that it's quick to iterate"; keep "the ability to dynamically configure ... how quickly backfills/migrations process data"; the backfill "must handle rows that already exist"; use tombstones so deleted rows "don't get resurrected by the backfill script"; iterate by primary key and "Never use `offset`"; "Track how fast you're going! - Stripe's online-migration pattern: dual write, backfill, switch reads with a comparison that alerts on mismatch, then remove the old path (search excerpt only). — [Stripe: Online migrations at scale](https://stripe.com/se/blog/online-migrations)
- Notion verified its backfill by sampling and dark reads, and split migration and verification between different people. — [Notion: Herding elephants](https://www.notion.com/blog/sharding-postgres-at-notion)
- Workflows give a durable, resumable runner for long jobs: per-instance pause, resume, restart from a step, terminate with rollback handlers, up to 25,000 steps per instance and 50,000 concurrent instances per account. — [Workflows Workers API](https://developers.cloudflare.com/workflows/build/workers-api/); [Workflows limits](https://developers.cloudflare.com/workflows/reference/limits/)

### Inferences
- Impact list: with tenant-keyed telemetry (section 3), an incident record can carry a query (time range, error codes, routes, versions) that produces the affected tenants, the number of failed requests each, and whether data was affected or only availability. The console should let the operator save that list on the incident, export it, and hand it to the communication step.
- Communication functions: per-tenant incident banner in the product; targeted email or in-app notice to affected tenants only; status page component mapping; a record on each tenant's timeline that it was affected by incident X (so support can answer later); post-incident summary per tenant.
- Fleet repair job runner, the largest piece of custom tooling in this area. Requirements drawn from the sources above:
  - Explicit tenant selector that refuses an empty or "all" selector without a separate, deliberate override (Diskerase).
  - Dry run that reports per tenant what would change, with counts and samples, and writes nothing.
  - Canary: run on an internal test tenant, then one consenting or low-risk real tenant, then widen.
  - Batches with configurable size, concurrency and delay, adjustable while running; automatic stop when the failure rate crosses a threshold.
  - Per-tenant state: pending, running, done, failed, skipped, with error and attempt count; resume from where it stopped; retry failed only.
  - Idempotency: each repair step keyed so that re-running a tenant is a no-op; the repair executes inside the tenant's object in a transaction and records that it ran.
  - Verification as a separate read-only pass, ideally written by someone other than the repair's author (Notion).
  - Before and after snapshots or a PITR bookmark captured per tenant before the change, so one tenant can be reverted.
  - Full audit: who started it, the code version, the selector, the reason, the approvals, the per-tenant outcome; attribution of resulting changes to the operator action rather than to a tenant user.
- A repair script should be reviewed and versioned like product code; ad-hoc edits through Data Studio do not scale past one tenant and leave no record in the product's own audit log.
- Each repair that recurs is toil by Google's definition and a candidate for a permanent console action.

- Status page vendor claims are from search excerpts; features and pricing were not verified.

## 8. Deployment safety: gradual deployments, per-tenant canary, version pinning, rollback after a migration

### Takeaway
Workers gradual deployments split traffic by percentage between two versions, and each Durable Object is assigned one version for the life of the deployment, but the operator cannot choose which objects (tenants) get the new version, so a tenant-ring rollout has to be built with flags or per-tenant settings inside one code version. Class lifecycle changes are atomic, cannot be rolled out gradually and block rollback past them; and a code rollback never rewinds data, so per-tenant schema changes must stay compatible with the previous code version.

### Cited Findings
- Gradual deployments "route a percentage of requests to the new version while the rest continue to be handled by the previous version"; routing is per request by default; created with `wrangler versions deploy`; "You can only create a gradual deployment with the last 100 uploaded versions". — [Gradual deployments](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/)
- "Workers currently only supports serving two different versions in one deployment." — [Version overrides](https://developers.cloudflare.com/workers/versions-and-deployments/version-overrides/)
- Durable Objects: "only one version of each Durable Object can run at a time"; "each Durable Object is assigned a Worker version based on the percentages you configured in your deployment. This version will not change until you create a new deployment"; when a version's percentage is raised in the same order, objects already on it are not moved back; an object is reset only when its assigned version changes. The page does not describe pinning a named object to a version. — [Gradual deployments with Durable Objects](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/with-durable-objects/)
- A bundle that defines both the Worker and the Durable Object class cannot deploy them independently, and "API changes should be forwards and backwards compatible" because mixed versions will talk to each other during a rollout. — [Gradual deployments with Durable Objects](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/with-durable-objects/)
- "Versions of Worker bundles that change Durable Object class lifecycle cannot be uploaded"; lifecycle changes "are atomic operations"; "Once a lifecycle change is deployed, rollbacks cannot take place to any version prior to the one that included the change"; "Durable Object lifecycle changes should be deployed independently of other code changes." — [Gradual deployments with Durable Objects](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/with-durable-objects/)
- With declarative `exports`: "`wrangler versions upload` does not apply lifecycle changes"; "Gradual deployments are not supported with `exports`" lifecycle changes; "Rollbacks cannot cross a lifecycle change"; "Storage backends are immutable once provisioned." — [Durable Objects migrations](https://developers.cloudflare.com/durable-objects/reference/durable-objects-migrations/)
- Rollback limits: only to "the 100 most recently published versions"; not allowed if a Durable Object lifecycle change happened in between, or if a bound R2 bucket, KV namespace or queue no longer exists. — [Rollbacks](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/)
- Version overrides: header `Cloudflare-Workers-Version-Overrides` (dictionary of Worker name to version ID); "A version override will only be applied if the specified version is in the current deployment", and the version can be at 0%; use case is smoke-testing a version in production before shifting traffic. The page does not mention Durable Objects. — [Version overrides](https://developers.cloudflare.com/workers/versions-and-deployments/version-overrides/)
- Version affinity sends requests with the same key to the same version while the deployment configuration is unchanged. — [Gradual deployments](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/)
- Observability by version: a `ScriptVersion` object in Workers Logpush; a version metadata binding exposes the version ID or tag in code; the Durable Object namespace Deployments tab shows requests, error rate and wall time per version, with an "actual vs. configured traffic split". — [Gradual deployments](https://developers.cloudflare.com/workers/versions-and-deployments/gradual-deployments/); [Changelog 2026-08-20](https://developers.cloudflare.com/changelog/post/2026-08-20-durable-objects-deployments-tab/)
- "Durable Object reset because its code was updated." occurs when an update is applied before the object hibernates, "with the `immediate` strategy, or when a `deferred` deployment reaches its `max_delay`"; only in-memory state is lost. — [DO troubleshooting](https://developers.cloudflare.com/durable-objects/observability/troubleshooting/)
- "If one Worker defines every class, a deploy can affect objects across all of those classes." — [DO architecture guidance](https://developers.cloudflare.com/durable-objects/best-practices/architecture-guidance/)
- Azure rings: canary (own test tenants and customers who want updates early), early adopter, users; "roll out updates on a tenant-by-tenant basis"; "Allow customers to temporarily but not permanently opt out"; three approaches are deployment stamps, feature flags and deployment rings. — [Azure: updates in multitenant solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/updates)

### Inferences
- Cloudflare's percentage split is a canary by share of objects, not by chosen tenant. The assignment rule is not documented, so the operator cannot predict or select which hotels move first. To put internal test properties and volunteer hotels first, the ring has to be a per-tenant attribute evaluated in code (a flag or a "release ring" setting on the tenant), with new behaviour behind it, all shipped in one Worker version.
- Deployment stamps in Azure's sense would mean separate Worker scripts and namespaces per ring. That is heavy on this platform because objects cannot be relocated or re-homed individually (section 9), so flags and rings are the practical choice.
- The version-override header helps smoke-test the stateless Worker at 0%, but since each object is bound to one version for the deployment, it should not be assumed to pick the version a given tenant's object runs. Not documented either way.
- Because of the two-version limit and the reset on reassignment, each step of a gradual rollout restarts the objects that move; in-memory state and WebSocket connections on those objects are dropped once per move.
- Rollback after a schema migration has run: code goes back, data does not. Safe practice is expand then contract: release N adds columns or tables that release N-1 ignores; the contract step ships only after the fleet view (section 1) shows every tenant on the new schema and N-1 is no longer a rollback target. The per-tenant escape hatch is PITR to the bookmark taken just before migration, at the cost of every write since.
- Console functions that follow: current deployment (versions and percentages), per-tenant ring and effective flags, tenants by code version last seen and by schema version, per-version error rate with tenant breakdown, a "hold rollout" signal, and a pre-deploy check that flags any pending class lifecycle change (which removes the rollback path).
- Recording a PITR bookmark per tenant at migration time is cheap and makes the per-tenant revert possible for 30 days.

### Gaps
- How objects are assigned to versions (hash of ID or otherwise), and whether the override header or version affinity can influence a specific object's version, is not documented on the pages read.
- The `immediate` versus `deferred` update strategy and `max_delay` appear only in the troubleshooting text; the configuration page was not located or read.
- Whether gradual deployments are formally GA is not stated on the page read.

## 9. Tenant data location and movement

### Takeaway
Jurisdiction (`eu`, `us`, `fedramp`) is fixed in the object's ID at creation and guarantees where the object runs and stores data; location hints are best effort and apply only at first creation; existing objects do not move ("Dynamic relocation ... is planned for the future"). Moving a tenant between jurisdictions, copying a tenant, and cloning a tenant into staging with PII scrubbed are therefore all application-level export and import jobs into a different object.

### Cited Findings
- Jurisdictions: `eu` (European Union), `us` (United States, added 2026-06-26), `fedramp` (FedRAMP-Moderate data centres). They "create Durable Objects that only run and store data within a region". Created through `env.NS.jurisdiction("eu")` or `newUniqueId({ jurisdiction })`. — [DO data location](https://developers.cloudflare.com/durable-objects/reference/data-location/); [Changelog 2026-06-26](https://developers.cloudflare.com/changelog/post/2026-06-26-durable-objects-us-jurisdiction/)
- "Workers may still access Durable Objects constrained to a jurisdiction from anywhere in the world. The jurisdiction constraint only controls where the Durable Object itself runs and persists data." Regional Services is the product for controlling where requests are handled. — [DO data location](https://developers.cloudflare.com/durable-objects/reference/data-location/)
- "A DurableObjectId will be logged outside of the specified jurisdiction for billing and debugging purposes." — [DO data location](https://developers.cloudflare.com/durable-objects/reference/data-location/)
- The jurisdiction is encoded in the ID string and readable inside the object as `ctx.id.jurisdiction`. — [Durable Object ID](https://developers.cloudflare.com/durable-objects/api/id/)
- "An object in a jurisdiction has a different ID from an object with the same name outside it. Use the same `jurisdiction` every time you route to an object." — [Agents routing options](https://developers.cloudflare.com/agents/runtime/routing/options/)
- "Durable Objects do not currently change locations after they are created"; footnote: "Dynamic relocation of existing Durable Objects is planned for the future." — [DO data location](https://developers.cloudflare.com/durable-objects/reference/data-location/)
- Location hints: `wnam`, `enam`, `sam`, `weur`, `eeur`, `apac`, `apac-ne`, `apac-se` (the last two added 2026-06-19), `oc`, `afr`, `me`; objects are not spawned in `sam`, `afr` or `me` and go to a nearby supported location. "Only the first call to `get()` for a particular Object will respect the hint." "Hints are a best effort and not a guarantee." — [DO data location](https://developers.cloudflare.com/durable-objects/reference/data-location/); [Changelog 2026-06-19](https://developers.cloudflare.com/changelog/post/2026-06-19-apac-ne-apac-se-location-hints/)
- By default an object is created near the first `get()` request; Cloudflare warns that pre-creating objects from an unrepresentative location hurts latency. — [DO data location](https://developers.cloudflare.com/durable-objects/reference/data-location/)
- A queue's dead-letter queue must share its jurisdiction, so Queues have jurisdictions too. — [Queues: dead letter queues](https://developers.cloudflare.com/queues/configuration/dead-letter-queues/)
- Class-level Transfer and Rename lifecycle changes move all objects of a class to another class; they are not per-object moves. — [DO class migrations (legacy)](https://developers.cloudflare.com/durable-objects/reference/durable-object-class-migrations-legacy/)
- 37signals planned region-based placement of tenant SQLite databases with a read-only replica per tenant on a second machine, and cited the failover edge cases as the reason the product launched on MySQL. — [37signals: Rails multi-tenancy](https://dev.37signals.com/rails-multi-tenancy/)

### Inferences
- A tenant's residency is decided at provisioning and is in practice permanent: the same tenant name under a different jurisdiction is a different, empty object. The routing layer must therefore store each tenant's jurisdiction and use it on every lookup; a wrong value creates a fresh empty object rather than an error.
- Provisioning from the operator's own location (for example a console action run from another continent) places the object near the operator unless a location hint is passed. Tenant creation should pass a hint derived from the property's country.
- Console functions that follow: show each tenant's jurisdiction and creation hint; residency report by tenant for compliance questionnaires; and a "move or copy tenant" job.
- Move or copy a tenant, as a job with the same controls as a fleet repair (section 7): put the source in read-only mode; export all tables in chunks; import into the target object (new jurisdiction, or a staging account); verify row counts and checksums per table; switch routing; keep the source read-only for a hold period; then delete it. Data held outside the object (the organisation object's vault and keys, R2 documents, KV projections, Workflows in flight, queued events) must be listed and handled per store.
- Clone into staging for reproduction: export, then scrub before import. Scrubbing rules belong in code (per table and column: drop, hash, or replace with synthetic values), and encrypted PII is best handled by not copying the keys at all, which leaves the ciphertext unreadable in staging. The clone action should be audited, time-limited (auto-delete), and blocked for tenants whose contract forbids it.
- PITR cannot be used to clone, since it restores only in place.
- The ID being logged outside the jurisdiction means tenant identifiers used as object names should not themselves contain personal or sensitive data.

### Gaps
- Not documented on the pages read: any way to change an existing object's jurisdiction; a timeline for dynamic relocation; whether location hints interact with jurisdictions.
- KV, R2 and Workflows data-location controls were not checked, so residency for projections, documents and workflow state is unverified.
- No published account of moving a Durable Object tenant between jurisdictions was found.

## 10. Secrets and key management operations

### Takeaway
The pattern in the literature is envelope encryption with a per-tenant key-encryption key wrapping per-subject data keys: rotation adds a key version and re-wraps, erasure destroys the subject's key (or the tenant's key at offboarding), and the weak points are plaintext copies elsewhere and backups of the key store. On this platform the 30-day PITR window is one such backup: a destroyed key inside a Durable Object remains recoverable by PITR until the window passes. Cloudflare-specific key-management features were not verified in this pass.

### Cited Findings
- PITR can restore any SQLite-backed object's full contents to any point in the past 30 days, and is on by default. — [SQLite storage API: PITR](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/); [Cloudflare blog: SQLite in Durable Objects](https://blog.cloudflare.com/sqlite-in-durable-objects/)
- "A Durable Object fully ceases to exist if, when it shuts down, its storage is empty." — [Access Durable Objects storage](https://developers.cloudflare.com/durable-objects/best-practices/access-durable-objects-storage/)
- `deleteAll()` atomically removes all SQL and KV data of a SQLite-backed object (and the alarm, from compatibility date 2026-02-24). — [SQLite storage API](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)
- A rollback to a Worker version whose secret values differ from the current deployment prompts for extra confirmation in the Deployments API (`?force=true` to proceed), which shows that secrets are versioned with Worker versions. — [Workers platform changelog, 2024-06-20](https://developers.cloudflare.com/workers/platform/changelog/)
- Crypto-shredding design (search excerpts only; blog and vendor material, not standards): "a per-tenant KEK in the key management service wraps per-subject DEKs stored in a key table"; tenant offboarding destroys the tenant KEK and a single erasure destroys the subject's DEK; rotation "adds a version and keeps old ciphertext readable" and re-wraps data keys; the approach "fails silently if plaintext copies exist anywhere: caches, search indexes, analytics exports, logs written before encryption"; keystore backups need their own erasure handling; whether shredding satisfies GDPR Article 17 is debated; policy should say whether "shred" is immediate, delayed for a legal hold, or a temporary disable. — [nhimg.org crypto-shredding guide](https://nhimg.org/crypto-shredding-guide); [krew-solutions ADR-0009](https://krew-solutions.github.io/ascetic-ddd-python/adr/0009-envelope-encryption.html); [DEV: You can't delete an event](https://dev.to/norbertrosenwinkel/you-cant-delete-an-event-gdpr-says-you-must-crypto-shredding-is-the-truce-26ak); [Gravitee: key management for crypto-shredding](https://gravitee.io/corpus/gen-1808/data-erasure/key-management-for-crypto-shredding.html); [AWS Builder Center: cryptographic erasure](https://builder.aws.com/content/3BOLPCayV1YAQD0ScQZ2Rc1YoeZ/cryptographic-erasure-a-data-deletion-strategy-using-aws-kms)
- Data Studio queries on production objects are audit logged by Cloudflare. — [Data Studio](https://developers.cloudflare.com/durable-objects/observability/data-studio/)

### Inferences
- If wrapped data keys live in the organisation object's SQLite, deleting a key row is not final for 30 days, because PITR can bring it back. An erasure certificate should therefore either state the date after which recovery is impossible (deletion plus 30 days) or rely on a second factor that is destroyed immediately and is not covered by PITR. The same reasoning applies to plaintext or ciphertext restored by a tenant PITR (section 2): a restore to a point before an erasure resurrects the erased subject's data and key together, so restore must re-apply erasures made since the bookmark. This needs an erasure ledger held outside the restored object.
- Operator-console functions for keys, none of which should ever display key material:
  - Inventory: per tenant, key versions with created, activated and retired dates, counts of data keys under each version, last rotation, next due.
  - Rotate: per tenant or fleet-wide, run as a tracked job (dry run, batches, progress, resume) that re-wraps data keys; show tenants still on a retired version.
  - Verify: decrypt-canary check per tenant (a known record decrypts under the active version), and a report of rows that fail to decrypt.
  - Erase: subject-level and tenant-level shredding as a workflow with legal-hold check, dual approval, and a certificate of destruction recording what was destroyed, when, by whom, the method, the stores covered (primary, projections, exports, logs), and the residual-recovery date.
  - Emergency: revoke or disable a tenant's key (a temporary lockout) distinct from destroy.
- Platform master-key rotation is a deployment-coupled operation (a secret change plus a re-wrap sweep), so it needs the same fleet view as schema migrations: tenants by master-key version.
- Derived copies must be in scope for erasure: KV projections, R2 documents (registration cards, invoices), analytics data points, logs (7 days in Workers Logs, three months in Analytics Engine), queue messages in flight and Workflow state.
- Key operations belong on the short list of actions that a global kill switch must not block when they discharge a legal duty.

### Gaps
- Cloudflare Secrets Store, Workers secrets rotation mechanics, and any Cloudflare KMS or customer-managed-key feature for Durable Objects, KV or R2 were not researched in this pass.
- No primary legal or standards source (for example regulator guidance on crypto-shredding and Article 17, or NIST key-management guidance) was read; the crypto-shredding findings are from search excerpts of blogs.
- Whether PITR history is retained after an object is emptied with `deleteAll()` is not documented, which matters for tenant-level erasure.

## 11. General SRE and multi-tenant operations references

### Takeaway
The three references say the same thing from different angles: AWS says tenant and tier must be first-class dimensions in every operational view and alert; Azure says a control plane must know which version each tenant runs and roll updates out by rings with tenant health watched before and after; Google says operational work that grows linearly with the number of tenants is toil to be engineered away, and that automation at scale needs sanity checks, rate limits and idempotency because it fails at scale too.

### Cited Findings
- AWS SaaS Lens: "The operations experience for SaaS environments introduces the need for additional mechanisms and tooling that can be used to create tenant-aware insights into the activity and consumption patterns of individual tenants and tiers." — [AWS SaaS Lens: tenant-aware operations](https://docs.aws.amazon.com/wellarchitected/latest/saas-lens/tenant-aware-operations.html)
- AWS SaaS Lens OPS 1 best practices: include tenant context in logs ("a tenant identifier and, if possible, a user-friendly tenant name"); "Use purpose-built, tenant-aware tools to enable proactive management of tenant workloads"; collect tenant activity, health, consumption, latency, feature-consumption and SLA metrics; analyse by tier and role; "Configure alerts and alarms that are triggered when tenants reach specific health states or performance thresholds"; keep history "to inform future architectural and operational decisions". — [AWS SaaS Lens OPS 1](https://wa.aws.amazon.com/saas.question.OPS_1.en.html)
- AWS SaaS Lens REL 2: "A resilient SaaS environment supports tenant-aware operations that enable proactive detection and resolution of tenant and system health issues" (search excerpt only). — [AWS SaaS Lens REL 2](https://wa.aws.amazon.com/saas.question.REL_2.en.html)
- Azure, control plane responsibility: know "which version of infrastructure, software, or feature each tenant uses, what they're eligible to migrate to, and the time-based data associated with those states." — [Azure: updates in multitenant solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/updates)
- Azure, update policy: identify tenants' requirements (maintenance windows, regulation, sensitive periods, rollback expectations); "If you leave cadence of your service updates entirely to your tenants' discretion, they might choose to never update"; keep the right "to deploy security patches, or other critical hotfixes, with minimal or no advance notice"; be "careful about enabling tenants to initiate their own updates" because it is complex. — [Azure: updates in multitenant solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/updates)
- Azure, external dependencies: "Record which tenants, deployment stamps, and product versions use each dependency version"; plan and test migrations before support ends. — [Azure: updates in multitenant solutions](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/considerations/updates)
- Azure, Deployment Stamps: stamps "can be used to implement deployment rings"; deployment of each stamp should be "predictable and repeatable"; use automation and infrastructure as code; tag resources with tenant or stamp identifiers; single-tenant stamps cost more, shared stamps keep the noisy-neighbour problem (search excerpts only). — [Azure: Deployment Stamps pattern](https://learn.microsoft.com/azure/architecture/patterns/deployment-stamp); [Azure: deployment and configuration](https://learn.microsoft.com/en-us/azure/architecture/guide/multitenant/approaches/deployment-configuration)
- Google SRE, toil: manual, repetitive, automatable, tactical, no enduring value, "linear in growth"; goal of keeping it "below 50% of each SRE's time"; "Toil becomes toxic when experienced in large quantities." — [Google SRE book: eliminating toil](https://sre.google/sre-book/eliminating-toil/)
- Google SRE, automation: value in consistency, a platform that centralises fixes and exposes metrics, faster repair and action; a hierarchy from no automation to autonomous systems; warnings from Diskerase and a wiped Bigtable cluster; "such procedures should be scoped over well-defined domains"; "the approach with the highest leverage actually occurs in the design phase"; operator deskilling when automation covers routine work. — [Google SRE book: automation](https://sre.google/sre-book/automation-at-google/)

### Inferences
- Mapped to this architecture, the references imply a small control plane beside the per-tenant objects holding, per tenant: identity and tier, jurisdiction, lifecycle state, schema version, code version last seen, release ring, flags and switches, key versions, storage size, last heartbeat, open incidents, and recent operator actions. Almost every console function in sections 1 to 10 reads from or writes to that registry. Cloudflare provides the per-object runtime and aggregated metrics; the registry and everything tenant-shaped is the application's.
- Split of responsibility, in summary:
  - Provided by Cloudflare: object isolation and durability; 30-day PITR per object; namespace metrics; logs and traces with object ID; Data Studio; queue DLQ, pause, purge and metrics; Workflow instance control; percentage rollouts and rollback of code; jurisdictions; an approximate rate limiter; a feature-flag service.
  - To be built: tenant registry and fleet view; schema-version tracking and sweeps; restore workflow with safeguards and reconciliation; export, clone and move; tenant-keyed telemetry, health and alerts; outbox and dead-letter browsing and replay by tenant; alarm watchdog; quotas and metering; kill switches and degraded modes with audit; incident impact lists and targeted communication; fleet repair runner; tenant rings; key rotation and erasure workflows with certificates; the operator audit log itself.
- Toil test for the console backlog: any task whose effort grows with the number of hotels (checking each tenant after a release, repairing the same data fault tenant by tenant, answering "what version is this hotel on") should become a console function or disappear by design.
- Google's deskilling warning argues for keeping the automated jobs observable (per-tenant state, dry-run output) and for rehearsing manual paths such as restore on staging.

### Gaps
- The AWS SaaS Lens operations chapter beyond the tenant-aware operations paragraph and OPS 1 was not read in full; REL 2 is from a search excerpt.
- The Azure Deployment Stamps and control-plane pages were not opened; the stamp findings are from search excerpts.
- Google's later SRE Workbook chapters (for example on canarying releases and on configuration) were not reviewed.
